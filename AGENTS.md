# Инструкции для ИИ-агентов

Этот файл читают агенты, работающие с репозиторием ProbablyWorks. Установка, команды запуска и архитектура
описаны в [README.md](README.md). Здесь — правила, которые нужно соблюдать при любых изменениях.

## Общие принципы

- Перед правками прочитайте `README.md` и релевантные документы: [docs/ui/RULEBOOK.md](docs/ui/RULEBOOK.md)
  и [docs/ui/WIDGET_BOOK.md](docs/ui/WIDGET_BOOK.md) для UI.
- Делайте полный результат: если меняете поведение, обновите тесты, локализацию, документацию и комментарии.
  Не оставляйте заглушки и `TODO` без причины и контекста.
- Не коммитьте и не пушьте без явной просьбы. Не меняйте `.idea/` и `.vscode/` без запроса.
- Комментарии и документация — на русском. Идентификаторы — на английском.

## Комментарии в коде

Уровень комментирования в проекте высокий. Его нужно поддерживать, а не снижать.

- Каждый публичный класс, метод и top-level функция получают `///`: что делают и что возвращают или бросают.
  Для нетривиальных модулей добавляется шапка `///` в начале файла (см. `lib/core/util/`).
- Комментарий объясняет **почему**, ограничения, граничные случаи и неочевидные связи с другими частями.
  Пересказ очевидного кода не нужен.
- При изменении логики обновляйте комментарии в той же правке. Устаревший комментарий хуже отсутствующего.
- Не оставляйте закомментированный код: это запрещено правилом DCM `avoid-commented-out-code`.
- `// ignore: <правило>` всегда сопровождается причиной через запятую или в соседней строке
  (правило `prefer-commenting-analyzer-ignores`).

## Проверки после изменений

Выполняйте проверки после каждой значимой правки и до того, как сообщить о завершении.

1. **Форматирование:** `dart format lib test` (проверка без записи: `dart format --output=none --set-exit-if-changed lib test`).
   Проект уже отформатирован, поэтому любой diff от `dart format` означает, что правка не отформатирована.
2. **Статический анализ Flutter:** `flutter analyze`. Замечаний быть не должно.
3. **DCM:** `dcm analyze lib test`. Замечаний быть не должно. Правила заданы в `analysis_options.yaml`, секция `dcm`.
4. **Тесты:** `flutter test`. Для локальной правки достаточно затронутых тестов, но перед завершением задачи
   прогоняйте всё. Интеграционные SSH-тесты пропускаются без `PW_SSH_PORT`, их не нужно поднимать без задачи.
5. **Кодогенерация:** если менялись аннотации `injectable`, `auto_route` или таблицы/схема `drift`, выполните
   `dart run build_runner build --delete-conflicting-outputs`.
6. Если приложение запущено через `flutter run`, после правок Dart-кода выполните hot reload или hot restart.

Пакеты `packages/pw_agent`, `packages/pw_client`, `packages/pw_server`, `packages/virtual_host` и `packages/virtual_git` этими командами не покрываются.
Каждый проверяют отдельно, из каталога пакета: `dart format lib test`, `dart analyze`,
`dcm analyze lib test`, `dart test`.

Если проверка не проходит из-за вашей правки, исправьте её. Не подавляйте замечания `ignore` без причины
и не отключайте правила в `analysis_options.yaml` ради прохождения проверки.

## Стиль кода

- Линтеры и правила заданы в `analysis_options.yaml`. Не обходите их, а следуйте им: например, `always_use_package_imports`,
  `require_trailing_commas`, `prefer_single_quotes`, `directives_ordering`, `sort_pub_dependencies`.
- Используйте короткий синтаксис Dart там, где читаемость не страдает: initializing formals (`this.x`),
  dot shorthands (`.new`, `.empty`), `??=`, `?.`, `=>` для однострочных функций, collection `if`/`for`, switch-выражения.
- Не используйте `print`. Логируйте через `AppLog` (`lib/core/logging/app_log.dart`) и не записывайте секреты:
  строки проходят через `Redactor`.
- Не редактируйте сгенерированные файлы (`*.g.dart`, `*.freezed.dart`, `*.config.dart`, `*.gr.dart`,
  `lib/l10n/generated/`). Меняйте источник и перегенерируйте.
- Архитектура: feature-first и clean architecture. UI-состояние — BLoC/Cubit, зависимости — `get_it` + `injectable`.
  Новый код размещайте в существующих слоях: `agent/`, `host/`, `core/`, `providers/`, `features/`, `app/`.
  Ядро виртуального хоста — пакет `packages/virtual_host`. Новый апплет стандартного набора кладётся туда.
  Git — отдельный пакет `packages/virtual_git`: он зависит от `virtual_host` и в стандартный набор не входит.
  Адаптер к Host, базе и политике остаётся в `lib/host/virtual/`.

## Локализация

- Любая строка для пользователя добавляется сразу в `lib/l10n/app_en.arb` и `lib/l10n/app_ru.arb`.
  Тест `test/l10n/arb_parity_test.dart` проверяет совпадение ключей.
- Dart-файлы переводов генерируются через `flutter gen-l10n`, руками их не правят.
- Технические значения (адрес хоста, имя модели, команда) можно не переводить.

## UI

- Цвета, отступы, радиусы, длительности и ширины берите из токенов (`package:app_ui`), а не литералами.
- Вместо стандартных виджетов Material используйте собственные: общие живут в `packages/app_ui/`,
  прикладные — в `lib/app/ui/` (таблица замен в `WIDGET_BOOK.md`). Экраны по-прежнему импортируют
  `package:probably_works/app/ui/ui.dart`.
- У каждого экрана и списка должны быть состояния: пустое, загрузка, ошибка, заблокировано.
- Golden-тесты обновляйте только при намеренном изменении внешнего вида:
  `flutter test --update-goldens test/app/ui/ui_kit_golden_test.dart`. Просмотрите новые эталоны перед коммитом.

## Безопасность и данные

- Ключи OpenRouter, пароли и passphrase SSH хранятся только в `SecretStore` (защищённое хранилище ОС), не в SQLite и не в файлах.
- Не добавляйте в код, тесты и логи реальные ключи и пароли. Для тестов используйте `lib/core/security/` (хранилище в памяти).
- Не ослабляйте политику исполнения: эскалация прав (`sudo`, `su`, `doas`) запрещена на уровне политики, а не настройки.
- Схему БД меняйте через `schemaVersion` и миграцию в `app_database.dart`, а миграцию покрывайте тестом в `test/core/db_migration_test.dart`.
  Существующие миграции не переписываются.

## Зависимости и supply chain

- Перед добавлением или обновлением зависимости проверьте версию и уязвимости через Sonatype MCP
  (`user-sonatype-mcp`: `getLatestComponentVersion`, `getRecommendedComponentVersions`, `getComponentVersion`).
- Добавляйте зависимости в `pubspec.yaml` в алфавитном порядке (`sort_pub_dependencies`), затем выполните `flutter pub get`
  и коммитьте `pubspec.lock` вместе с `pubspec.yaml`.
- Git-зависимость `openrouter` зафиксирована на тег. Не переводите её на ветку.
- Android-сборка использует Gradle (`android/`, `gradlew`). Сборочные артефакты в `build/` не правьте.

## Коммиты

- Формат: Conventional Commits, `тип(область): описание`. Тип на английском, описание и тело на русском.
- Тип — из полного списка в `.gitmessage` (`feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`),
  даже если конкретный тип в истории ещё не использовался.
- Область необязательна. Список областей — в `.gitmessage`.
- Описание: глагол в инфинитиве («добавить», «улучшить», «удалить»), без точки в конце, до 72 символов.
- Тело: 2–4 предложения о причине изменения и о поведении после него, перенос строк на 72 символах.
  Не перечисляйте файлы и классы: это видно в diff.
- Для несовместимых изменений добавьте строку `BREAKING CHANGE:` в тело коммита.
- Шаблон подключён через `commit.template` (`git config commit.template .gitmessage`).
