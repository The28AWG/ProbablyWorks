# Удалённый доступ через недоверенный relay

> **Статус:** идея дальнейшего развития. Ничего из описанного здесь не
> реализовано. Документ фиксирует задачу, выбранную архитектуру,
> компромиссы и открытые вопросы. Структура протокола, конкретная
> криптография и детали UX требуют отдельного проектирования, проверки и
> ревью. Запись в `CHANGELOG.md` не добавляется, пока изменение не
> реализовано и не проверено.

**Выбранный транспорт:** WSS с прикладным E2E.

## 1. Задача

Нужен удалённый доступ к агенту, который находится за NAT и не имеет прямого
IP. Клиент не должен требовать проброса портов. Схема:

- агент регистрируется на мастер-хосте (relay);
- клиент спрашивает relay, есть ли агент, и открывает канал;
- трафик идёт между клиентом и агентом через relay;
- relay не должен иметь возможности командовать агентом;
- один агент — много окон и устройств;
- пользователь не должен вручную возиться с ключами и токенами.

Relay не считается скомпрометированным. Ограничение вводится на уровне
архитектуры: даже добросовестный оператор relay не должен получать
техническую возможность читать трафик или отправлять команды агентам. Это
не только вопрос доверия к людям, но и сокращение поверхности атаки: у
оператора просто не должно быть ключей и права одобрять устройства.

## 2. Что уже есть в проекте

Текущая архитектура к этой идее близка:

- `packages/pw_server/lib/src/api/api_server.dart` — HTTP/SSE API поверх
  агента. По умолчанию слушает loopback, требует `Authorization: Bearer`,
  ограничивает тело запроса 8 MiB, лимитирует запросы по IP, ведёт
  `logs/api-access.log`, держит SSE с heartbeat 15 секунд.
- `packages/pw_client/lib/src/remote_agent_api.dart` — `RemoteAgentApi`
  принимает готовый `http.Client`, умеет SSE, рукопожатие клиентской сессии,
  heartbeat и переподключение. Это главная точка расширения: новый транспорт
  можно добавить, не переписывая все методы API.
- `docs/agent/MULTI_VIEW.md` — модель «один агент — много окон и устройств»:
  сессии, присутствие, ревизии, список экранов.
- `packages/pw_agent/lib/core/notify/push_service.dart` — демон уже умеет
  исходящие HTTPS-запросы к внешнему push-relay. Значит исходящий WSS до
  мастер-хоста не является чужеродной моделью.
- `docs/agent/DAEMON.md` — текущее описание удалённого доступа и требований
  к авторизации; relay-подход должен сохранить loopback-модель и явную
  авторизацию.

Ограничения текущего состояния:

- встроенного TLS у демона нет;
- удалённый профиль задаётся `baseUri` и токеном, которые пользователь
  вводит вручную;
- `lib/app/profiles/agent_profile.dart` знает только `local` и `remote`, без
  relay-профиля;
- `sendSessionClosing` в `lib/core/session/` ходит напрямую через HTTP и
  обходит `RemoteAgentApi`;
- `ApiServer` лимитирует запросы по IP, а через туннель все клиенты будут
  выглядеть как `127.0.0.1`;
- один API-токен на сервер, без отдельного токена устройства. В
  `MULTI_VIEW.md` уже отмечено, что для отзыва одного устройства нужен
  отдельный `deviceToken` или его аналог.

## 3. Референсная архитектура

```text
клиент                         мастер-хост                         агент
┌──────────────┐   WSS + E2E   ┌──────────────┐   WSS + E2E   ┌─────────────────┐
│ RelayHttp    │──────────────►│   relay      │◄──────────────│ agent tunnel    │
│ Client       │               │  (routes)    │               │ (pw_server)     │
└──────────────┘               └──────────────┘               └────────┬────────┘
                                                                       │ loopback
                                                                       ▼
                                                             127.0.0.1:7787
                                                             ApiServer
```

Роли:

1. **Relay (мастер-хост)** — публичный или self-hosted сервис с двумя
   WSS-endpoint'ами: регистрация агента и подключение клиента. Хранит только
   `agentId → активный туннель` и `online/lastSeen`. Полезную нагрузку не
   читает. Для MVP может быть без БД.
2. **Agent tunnel** — часть демона. Сам открывает исходящее WSS-соединение,
   регистрируется, держит keepalive, принимает E2E-кадры и превращает их в
   HTTP-запросы к локальному `127.0.0.1:7787`, а ответы и SSE-поток — обратно
   в кадры.
3. **Client transport** — `RelayHttpClient implements http.Client` в
   `pw_client`. Умеет `send()` с потоковым ответом (нужно для SSE), отмену
   запроса и мультиплексирование нескольких запросов в одном WSS.
4. **Pairing/discovery** — агент регистрируется на relay; клиент спрашивает
   `GET /agents/{id}/status`, получает `online/lastSeen`, затем открывает
   канал. Для доступа к relay — отдельный relay-токен, не API-токен агента.

Принципы relay:

- relay — это rendezvous, а не CA;
- relay не хранит приватные ключи, не генерирует их и не эскроуит;
- relay не одобряет устройства и не имеет админ-API «разрешить агента»;
- relay видит только обезличенные идентификаторы, метаданные и шифротекст;
- relay может ронять и задерживать соединения, но не может читать или
  подделывать полезную нагрузку.

## 4. Модель безопасности

### 4.1. Границы доверия

| Компонент | Доверяем? | Что видит | Что может |
|---|---|---|---|
| Агент | Да, это доверенная часть | Ключи, трафик, команды | Выполнять команды, одобрять устройства |
| Клиент | Да, это доверенная часть | Ключи, трафик | Инициировать запросы |
| Relay | Нет в части содержимого и команд | `agentId`, метаданные, шифротекст | Маршрутизировать, ронять, задерживать, видеть размеры/время |
| Web-хостинг | Должен быть доверенным | HTML/JS приложения | Подменить клиент и украсть ключи |
| OS keychain | Да | Приватные ключи | Хранить и защищать |

Ключевой принцип: **relay — rendezvous, а не CA.** Он не хранит ключи, не
выдаёт сертификаты, не эскроуит секреты и не одобряет устройства.

### 4.2. E2E и взаимная аутентификация

Чтобы relay не мог командовать агентом, нужно одновременно:

1. relay никогда не видит API-токен и долгоживущие секреты;
2. агент аутентифицирует клиента внутри E2E;
3. клиент пиннит ключ агента;
4. кадры защищены AEAD и replay protection;
5. tunnel не исполняет команды relay и не превращает control-кадры в
   API-запросы.

Высокоуровневая схема:

- у агента есть долгоживущий identity-ключ (Ed25519 или P-256);
- у каждого устройства есть свой device-ключ;
- при сопряжении клиент получает и пиннит публичный ключ агента;
- агент хранит allowlist публичных ключей устройств;
- handshake использует эфемерный ECDH (X25519 или P-256) и подписи/доказательства
  обеих сторон;
- из общего секрета через HKDF выводятся session keys;
- кадры шифруются AEAD (AES-GCM или ChaCha20-Poly1305) с nonce/sequence и AAD;
- replay protection — монотонные sequence numbers в рамках сессии;
- новое соединение — новые эфемерные ключи, старые кадры в него не вставить.

Точная конструкция handshake, алгоритмы и формат кадров **не зафиксированы**.
Это тема отдельного проектирования и ревью. Нельзя просто «придумать свой
Noise» без тестовых векторов и проверки.

### 4.3. Что relay может и не может

Если схема выше реализована корректно:

**Не может:**

- читать запросы, ответы, SSE и токен;
- подделать запрос или ответ;
- выдать себя за агента клиенту (пиннинг);
- выдать себя за клиента агенту (device auth);
- незаметно повторить принятый кадр (sequence/replay);
- отправить агенту команду через control-канал, если tunnel не превращает
  control-кадры в API-запросы.

**Может:**

- ронять, задерживать, блокировать соединения (DoS);
- видеть метаданные: кто, когда, с каким агентом, сколько байт;
- пытаться подбирать пароли/токены, если relay-аутентификация слабая;
- атаковать реализацию протокола, если в ней ошибка.

Relay не может обеспечить availability, и это надо честно писать. Он также
может видеть факт подключения и объём трафика. Если это критично, нужны
padding/cover traffic, но это отдельная задача.

### 4.4. API-токен

API Bearer-токен должен ходить **только внутри E2E**. Если relay видит
`Authorization: Bearer`, он может командовать агентом, даже если тело
зашифровано. У relay должен быть свой отдельный токен для регистрации и
маршрутизации.

Дополнительный шаг QoL: клиент вообще не хранит API-токен. Туннель на
агенте после E2E-аутентификации сам добавляет локальный
`Authorization: Bearer <token>` к запросу в `127.0.0.1:7787`. Тогда:

- клиент не хранит токен;
- relay не видит токен;
- пользователь не вводит токен;
- API-токен остаётся внутренним секретом агента.

Для per-device отзыва всё равно нужен allowlist device-ключей, а не один
общий токен.

### 4.5. Endpoint trust

E2E защищает канал, но не защищает от компрометации endpoint'а:

- если агент скомпрометирован, ключи и команды скомпрометированы;
- если клиент скомпрометирован, его device-ключ и сессия скомпрометированы;
- если web-клиент раздаётся с origin relay, оператор relay контролирует JS
  и может украсть ключи. E2E этого не предотвращает.

Поэтому web-клиент лучше раздавать с отдельного доверенного origin, а relay
использовать только для WSS. Native-клиенты в этом смысле проще: приложение
подписано и установлено, relay не может подменить код.

## 5. Сопряжение и QoL

### 5.1. Принцип

Пользователь не должен видеть ключи. Он должен видеть:

- «Добавить устройство»;
- QR или кнопку «Скопировать ссылку»;
- «Chrome на Linux, разрешить?»;
- список устройств и «Отозвать».

Ключи генерируются, хранятся и проверяются автоматически.

### 5.2. Лучший UX: QR/ссылка + самоподтверждающийся ID + локальное одобрение

Сценарий:

1. На агенте: **Настройки → Удалённый доступ → Добавить устройство**.
   Агент на 5 минут включает режим сопряжения и показывает QR-код и ссылку.
2. На клиенте: **Добавить агента → Сканировать QR** (или открыть ссылку).
3. Клиент подключается через relay, проходит E2E-рукопожатие.
4. На агенте появляется запрос:
   > Новое устройство: Chrome на Linux. Код: 4821. Разрешить?
5. Пользователь нажимает **Разрешить**.
6. Готово. Клиент сохраняет агента, агент сохраняет устройство.

Дальше клиент подключается автоматически. Потерянное устройство отзывается
одной кнопкой в списке устройств.

### 5.3. Что внутри

- **Агент** при первом запуске генерирует identity-ключ. Приватный ключ лежит
  в `SecretStore`/OS keychain, публичный — в БД.
- **`agentId` — это отпечаток публичного ключа агента**, а не произвольный id,
  выданный relay. Например, `base32(SHA-256(pubkey))`. Тогда клиент может
  проверить: агент, к которому он подключился, действительно тот, чей ключ
  зашит в QR. Relay не может подсунуть другого агента с тем же id.
- **Клиент** при сопряжении генерирует свой device-ключ. Приватный ключ — в OS
  keychain (native) или non-extractable `CryptoKey` в IndexedDB (web).
  Публичный уходит агенту.
- **Relay** видит только `agentId`, публичные ключи в момент рукопожатия и
  шифротекст. Он не может подписать handshake за агента или клиента.
- **Одобрение — локальное.** Relay может инициировать запрос, но не может его
  одобрить. Агент принимает только те device-ключи, которые пользователь
  явно разрешил.
- **API-токен не нужен клиенту.** Туннель на агенте добавляет его локально
  после E2E-аутентификации.
- **Сессии и presence** остаются как сейчас: несколько устройств — несколько
  device-ключей и клиентских сессий.

### 5.4. Почему это защищает от недоверенного relay

- Relay не знает приватный ключ агента → не может выдать себя за агента.
- Relay не знает приватный ключ устройства → не может выдать себя за клиента.
- Клиент проверяет, что публичный ключ агента хешируется в `agentId` из QR →
  relay не может подменить агента.
- Агент принимает только device-ключи из локального allowlist → relay не
  может «протолкнуть» своё устройство.
- Relay не участвует в одобрении → у него нет админ-API «разрешить
  устройство».
- Relay может только ронять соединение, задерживать его и видеть метаданные.

### 5.5. Сопряжение по ссылке

Ссылка вида:

```text
https://app.example/pair#relay=...&agent=...&nonce=...
```

или deep link:

```text
probablyworks://pair?relay=...&agent=...&nonce=...
```

Секрет/nonce в fragment (`#`) не уходит на сервер при открытии ссылки. Для web
это важно: статический хостинг не видит fragment.

Для desktop-to-desktop без камеры: кнопка **«Скопировать ссылку»** и вставка
в клиент. Для телефона — QR. Для web — открыть ссылку в браузере.

### 5.6. Режим сопряжения вместо постоянного кода

QR/ссылка живут 5 минут и содержат одноразовый nonce. Агент принимает
pairing-запросы только в этом окне. Это:

- снижает спам от relay;
- не требует постоянного «кода устройства»;
- позволяет добавлять устройства только тогда, когда пользователь сам открыл
  режим.

### 5.7. Подтверждение на агенте, а не TOFU

TOFU («первый, кто подключился, тот и свой») против недоверенного relay не
работает: relay может оказаться первым. Нужен локальный approve на агенте.
Это одна кнопка, зато настоящая граница доверия.

Если хочется защиты от гонки, когда QR увидел кто-то ещё:

- клиент показывает короткий код (например, 4 цифры), агент показывает тот же;
- пользователь сверяет;
- код выводится из E2E-транскрипта, relay не может его подделать, не зная
  ключей.

Для обычного сценария достаточно QR + approve. Код — fallback.

### 5.8. Headless-агент

Если у агента нет GUI:

- `pw_server pair` печатает QR (ASCII) и ссылку в терминале;
- `pw_server devices` показывает список;
- `pw_server devices approve <id>` / `revoke <id>` — явное действие;
- либо локальный GUI, подключённый к демону по loopback, показывает тот же
  запрос.

Пользователь уже имеет SSH/локальный доступ к агенту, чтобы включить
сопряжение. Это и есть корень доверия. Через relay pairing-ссылку передавать
нельзя: она должна идти по доверенному каналу (экран, SSH, локальный GUI).

### 5.9. Устройства и отзыв

- Список: имя, платформа, когда добавлено, последняя активность.
- «Отозвать» удаляет публичный ключ устройства на агенте и рвёт активные
  сессии.
- Остальные устройства не затрагиваются: у каждого свой ключ.
- Никакой «ротации ключей» в UI. Потерянное устройство просто отзывается,
  новое сопрягается заново.

### 5.10. Восстановление без ключей

- Потеряли устройство → отозвали, добавили новое.
- Переустановили агент → новый identity-ключ, все устройства сопрягаются
  заново. Для single-user продукта это нормально.
- Если нужна миграция агента на новую машину без пересопряжения — отдельный
  advanced-сценарий: старый агент показывает QR с зашифрованным переносом
  identity-ключа, новый импортирует. Это не обязательный сценарий и не должен
  усложнять обычный UX.
- Обязательных recovery-кодов и «сохраните ключ в надёжном месте» быть не
  должно.

### 5.11. Web-клиент

Если relay раздаёт web-приложение со своего origin, оператор relay
контролирует JS и может украсть device-ключ или сессионные ключи. E2E не
спасает от компрометации endpoint'а. Поэтому:

- web-клиент лучше раздавать с отдельного доверенного origin;
- device-ключ хранить как non-extractable `CryptoKey` в IndexedDB, а не в
  `localStorage`;
- для WebCrypto выбирать P-256 + AES-GCM как наиболее переносимый набор;
- если пользователь очистил хранилище браузера — просто сопрягает устройство
  заново;
- passkeys/WebAuthn — возможное future-направление: приватный ключ не покидает
  аутентификатор, но это сложнее и требует RP ID/верификации. Не для MVP.

Native-клиенты в этом смысле проще: приложение подписано и установлено,
relay не может подменить код. Ключ лежит в OS keychain/Keystore/Secure
Enclave.

### 5.12. Fallback-сценарии

- **Нет камеры:** «Скопировать ссылку» → вставить в клиент.
- **Нет GUI у агента:** CLI с QR/link и approve/revoke.
- **Хочется короткий код:** 6–8 цифр + approve на агенте + rate limit. Если
  relay недоверенный и код короткий, в идеале PAKE (SPAKE2/OPAQUE), чтобы
  relay не мог офлайн подбирать. Но PAKE в Dart — отдельная зависимость и
  риск; для MVP проще QR/ссылку или высокоэнтропийный одноразовый код.
- **Нужно сверить код:** 4–6-значный SAS из транскрипта на обоих экранах.
- **Уже есть доверенное устройство:** оно может одобрить новое (device
  delegation) — приятный QoL, но это отдельная модель прав; для MVP
  достаточно approve на агенте.

### 5.13. Чего не делать

- Не просить пользователя копировать публичные/приватные ключи.
- Не давать relay генерировать, хранить или эскроуить ключи.
- Не выводить E2E-ключи из пароля/SSO relay: оператор relay знает пароль.
- Не использовать API Bearer-токен как pairing-код или relay-пароль.
- Не полагаться на TOFU без out-of-band якоря.
- Не делать постоянные pairing-ссылки/коды без TTL.
- Не хранить приватные ключи в `localStorage` или открытом виде в БД.
- Не показывать отпечатки ключей как основной UX — только в «Дополнительно».
- Не раздавать web-клиент с origin relay, если relay не доверяем.

## 6. Что придётся изменить в коде

1. **Новый пакет `packages/pw_relay`** — WSS-сервер, реестр агентов,
   маршрутизация кадров, лимиты, логирование без payload. Лучше отдельный
   пакет/бинарник, а не часть `pw_server`: у relay другая модель угроз и
   другой жизненный цикл.
2. **Общий пакет протокола** — типы кадров, streamId, sequence, codec. Его
   используют relay, агент и клиент. E2E-криптография — либо там же, либо в
   отдельном `pw_e2e`.
3. **Agent tunnel в `pw_agent`/`pw_server`** — исходящий WSS, регистрация,
   reconnect/backoff, keepalive, приём кадров, форвардинг в локальный API.
   Запускать в демоне; в embedded-GUI — только на native и с оговоркой, что
   при закрытии приложения доступ пропадает.
4. **`RelayHttpClient` в `pw_client`** — `http.Client`, который поддерживает
   `send()`, потоковый ответ, SSE, отмену. `RemoteAgentApi` уже принимает
   `http.Client`, поэтому большая часть API не меняется.
5. **Профиль relay** — в `lib/app/profiles/agent_profile.dart` сейчас только
   `local/remote` и `baseUri`. Нужен новый kind: relay URL, `agentId`,
   пиннинг ключа, id устройства. `ProfileService._remoteFor` должен создавать
   `RemoteAgentApi` с нужным клиентом.
6. **`sendSessionClosing`** — в `lib/core/session/` он ходит напрямую через
   HTTP и обходит `RemoteAgentApi`. Для relay-профиля его надо либо провести
   через тот же транспорт, либо не отправлять (сессию закроет обрыв SSE/TTL).
7. **Rate limit и аудит** — сейчас `ApiServer` лимитирует по IP, а через
   tunnel все запросы придут с `127.0.0.1`. Нужен per-client лимит в туннеле
   или ключ по аутентифицированному E2E-клиенту. В `api-access.log` `remote`
   тоже станет loopback; надо логировать fingerprint E2E-ключа/устройства.
8. **Настройки, БД, секреты** — relay URL/agentId/allowlist устройств в БД,
   приватные ключи и relay-токен только в `SecretStore`. Миграция схемы и
   тест миграции по правилам проекта.
9. **UI и локализация** — раздел «Удалённый доступ» на агенте (включить
   relay, показать pairing-код, список устройств, отзыв), добавление
   relay-профиля на клиенте, статус online/offline. Строки сразу в
   `app_en.arb` и `app_ru.arb`.
10. **Тесты** — codec, handshake, test vectors, replay, подмена ключа,
    мультиплексирование, SSE, отмена, reconnect, большие тела, rate limit,
    интеграция «демон ↔ relay ↔ клиент», web-тест. Плюс `flutter analyze`,
    DCM, форматирование, как требует `AGENTS.md`.
11. **Упаковка и эксплуатация** — отдельный бинарник/контейнер relay,
    systemd/Docker, TLS/WSS, метрики, лимиты, инструкция по self-hosted.
    Relay за TLS-терминатором — нормально: E2E всё равно защищает payload.

## 7. Риски и ограничения

- **Агент должен быть онлайн.** Если машина спит или процесс убит, relay
  покажет offline. Очереди сообщений на relay в MVP лучше не делать: это
  хранение данных и новая модель доступа. Для телефонов фоновые ограничения
  делают канал прерывистым.
- **Масштабирование relay.** Агент и клиент должны попасть на один экземпляр
  relay. Для MVP — один инстанс; дальше — sticky routing по `agentId`,
  consistent hashing или общая шина.
- **SSE и backpressure.** Один WSS — одна TCP-труба. Нужны chunked-кадры,
  ограниченные буферы, per-stream credits и отмена. Иначе один медленный
  SSE-поток или большое вложение задержит остальное.
- **Повторы и идемпотентность.** При обрыве in-flight запросы падают.
  Существующие `clientMessageId` и ревизии закрывают часть мутаций, но не
  все; нужна явная политика retry.
- **Задержка.** Лишний хоп заметен для терминала и стриминга токенов. Позже
  можно добавить hole punching/QUIC, но не в MVP.
- **Безопасность relay как сервиса.** Публичный relay — это auth, квоты,
  rate limit, max frame size, max connections, защита от slowloris, DDoS,
  политика логов и retention. Self-hosted сильно проще.
- **Приватность метаданных.** Relay видит, кто с кем соединяется и сколько
  передаёт. Если это критично — padding/cover traffic, но это отдельная
  задача.
- **Криптография.** Не стоит изобретать протокол без ревью. Нужны проверенные
  примитивы, test vectors и, желательно, внешний аудит. Добавление
  `cryptography`/`web_socket_channel` — по правилам проверки зависимостей.
- **Web-ключи.** Non-extractable `CryptoKey` лучше, чем секрет в
  `localStorage`, но XSS-риск остаётся. Это надо честно писать в
  документации.
- **Ops и юридика.** Публичный relay — это сервис с abuse, retention,
  приватностью и квотами. Self-hosted снимает часть этих вопросов.

## 8. Этапы

1. **Спецификация и модель угроз** — `REMOTE_RELAY.md` уже фиксирует
   направление; дальше нужен отдельный протокол: кадры, handshake, pairing,
   что relay видит/не видит, лимиты.
2. **Прототип маршрутизации** — простой WSS relay без E2E. Проверить
   discovery, reconnect, SSE и профиль relay. Это ещё не даёт «relay не
   может командовать», но проверяет транспорт и мультиплексирование.
3. **E2E и pairing** — device-ключи, AEAD, replay, allowlist, отзыв, тесты.
   Здесь появляется нужная гарантия.
4. **Web и hardening** — WebCrypto, web-клиент, лимиты, аудит, упаковка
   relay, метрики.
5. **Продукт** — multi-agent, per-device revocation, квоты, hole punching,
   мобильный фон.

Оценка сроков не делалась. По объёму это отдельная подсистема, сопоставимая с
текущим удалённым API, а не маленькая надстройка.

## 9. Открытые вопросы

Это то, что мы ещё не обсуждали и что нужно решить отдельно:

- **Структура протокола:** формат кадров, streamId, sequence, ACK, окна,
  отмена, сжатие, максимальные размеры, версионирование.
- **Handshake и криптография:** Noise IK/XX или собственная конструкция,
  P-256/X25519/Ed25519, AEAD, HKDF, test vectors, внешнее ревью.
- **Pairing:** QR vs ссылка vs короткий код; PAKE или SAS; поведение без
  камеры; deep links; headless-сценарии.
- **Relay API:** регистрация, discovery, auth, аккаунты, квоты, relay-токен,
  формат `agentId`, self-hosted vs hosted.
- **Per-device tokens vs tunnel token injection:** нужен ли клиенту
  API-токен вообще; как отзывать одно устройство; как мигрировать текущие
  профили.
- **Rate limit и аудит:** как ключевать лимиты через loopback; что писать в
  `api-access.log`; как не доверять spoofable-заголовкам.
- **Multi-client presence:** как relay-сессии соотносятся с `clientId`,
  `sessionId` и списком экранов; что делать с двумя вкладками и
  уникальностью соединения.
- **Масштабирование relay:** sticky routing, consistent hashing, общая шина,
  кластер, лимиты на соединения.
- **Web-хостинг:** где раздавать web-клиент, если relay не доверяем; SRI,
  CSP, версионирование, обновления.
- **Мобильный фон:** что делать, когда агент на телефоне убит системой;
  нужен ли push-wake.
- **Hole punching / direct path:** нужен ли прямой канал после rendezvous,
  QUIC/WebRTC, когда relay только signaling.
- **Device transfer / recovery:** перенос identity агента на новую машину;
  нужен ли recovery-код или это advanced-сценарий.
- **Data retention / privacy / abuse:** что relay хранит, сколько, как
  реагирует на abuse, какие логи и метрики.
- **Упаковка и релиз:** отдельный бинарник relay, Docker, systemd, CI,
  подпись, обновления.
- **Тестовая стратегия:** фейковый relay, интеграционный стенд
  «демон ↔ relay ↔ клиент», chaos-тесты, web-тесты, тесты crypto.
- **Совместимость:** версия протокола, старые клиенты, миграция профилей,
  откат.
- **Что не решать сейчас:** конкретный vendor relay, биллинг, multi-tenant
  роли, полный offline-очередь, мобильный фон. Это можно отложить.

## 10. Рекомендация

- Выбранный транспорт — **WSS relay + прикладной E2E**: он проще для
  интерактивного SSE, даёт полный контроль над backpressure, отменой и
  отсутствием stale-команд.
- Сопряжение — **QR/ссылка + самоподтверждающийся `agentId` + pairing mode +
  локальный approve + автоматические ключи**. Пользователь не должен видеть
  ключи и токены.
- Relay — **rendezvous, не CA**: без ключей, без эскроу, без права одобрять
  устройства.
- API оставить на loopback; туннель добавляет локальный токен после
  E2E-аутентификации.
- Web-клиент раздавать с доверенного origin, если relay не доверяем.
- Следующий шаг, когда вернёмся к разговору: отдельный протокол с кадрами,
  handshake, тестовыми векторами и PoC. До этого `CHANGELOG.md` не трогаем.
