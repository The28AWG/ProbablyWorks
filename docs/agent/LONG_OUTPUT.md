# Длинный вывод и вложения: пределы и постраничное чтение

## Зачем

Один результат инструмента или одно вложение не должны занимать всё окно
модели. Сжатие истории здесь не помогает: оно режет историю только по границе
`user`/`assistant`, чтобы не разрывать пару `tool_call`/`tool_result`. Значит,
слишком большой результат не сокращается вообще, и запрос не помещается в окно.

Поэтому предел ставится на каждый результат по отдельности, а полный текст
остаётся доступен через инструмент чтения.

## Что видит модель

| Источник | Что уходит в контекст |
|---|---|
| Вывод команды | Хвост до `toolOutputForModelChars` (по умолчанию 60 000) |
| `read_file` | Не больше `toolOutputForModelChars / 2` за вызов, дальше `offset` |
| MCP и плагины | Хвост до `toolOutputForModelChars`, полный текст — в запуске |
| `load_skill` и другие инструменты состояния | Хвост до `toolOutputForModelChars`, полный текст — в запуске |
| Текстовое вложение | Превью до `attachmentInlineChars` (по умолчанию 4 000) |
| Бинарное вложение (PDF, картинка) | Отдельной частью сообщения, байтами; в текст не попадает |

Предел один для всех источников: короткий ответ уходит как есть, длинный
получает шапку с `run_id`, размером, показанной частью и подсказкой дочитать.

## Постраничное чтение

`read_run_output` читает сохранённый текст в одном формате для двух источников.

- `run_id` — сохранённый вывод запуска инструмента.
- `attachment` — текст файла, приложенного к сообщению этого чата.
  `message_id` уточняет сообщение, если имя повторяется.

Ровно один из `run_id` и `attachment` обязателен.

Режимы:

- `tail` (по умолчанию) — последние `limit` символов, как в терминале;
- `chunk` — окно `limit` символов с точного `offset`;
- `grep` — поиск по строкам с окружением, номерами строк и смещениями.

Смещения считаются в символах, а не в байтах: значение из `tail` можно сразу
передать в `chunk`. Для поиска по длинному логу `grep` дешевле, чем чтение
всего текста.

Вывод запуска хранится хвостом: старые строки вытесняются (`logOutputDbBytes`).
Пока команда идёт, читается живой буфер в памяти, и смещения в нём сдвигаются
по мере поступления вывода.

## Вложения

Текст вложения хранится в самом сообщении (`ChatMessage.attachments[].content`),
поэтому дочитать его можно и после перезапуска, и на любой платформе: файл на
диске больше не нужен.

Превью ужимается, когда запрос не влезает в мягкий порог окна модели
(`softContextRatio` от `contextLimit - contextReserveTokens`). Ужимается только
превью вложений — остальное сокращает сжатие истории. В крайнем случае превью
становится нулевым: модель получает метаданные, имя файла и подсказку дочитать.
Сообщение пользователя при этом остаётся целым.

Ссылку на файл вместо содержимого использовать нельзя: поведение различается по
платформам. На desktop пикер отдаёт реальный путь, на Android — копию в кэше,
которая удаляется после чтения, на iOS и в web пути нет вовсе, а на iOS ещё и
нет локального Host. Поэтому текст передаётся содержимым, а не путём.

Бинарные файлы идут модели отдельной частью в первом запросе хода. Предел
`attachmentMaxBytes` ограничивает их размер не из-за окна модели, а чтобы не
тянуть слишком тяжёлые файлы. Текстом они не читаются: `read_run_output` на
такое вложение отвечает отказом с причиной.

## Старые результаты в истории

Предел на один результат не спасает длинную задачу: после десятка шагов полные
результаты инструментов всё ещё занимают историю. Поэтому ContextBuilder
заменяет тело старых результатов выжимкой, а вызов и его аргументы оставляет.

- Держатся целиком результаты последних `toolOutputKeepSteps` шагов модели
  (по умолчанию 6): это свежий контекст, на который модель ещё опирается.
  Результаты текущего хода пользователя не маскируются, даже если шагов в нём
  больше лимита: модель ещё работает с ними.
- В выжимке остаётся начало вывода (`toolOutputPreviewChars`, по умолчанию 200),
  имя инструмента и подсказка перечитать сохранённый вывод или повторить вызов,
  только если это безопасно. Короткий вывод не получает заголовок: маркер
  добавлял бы больше текста, чем экономил.
- Результаты, подтверждающие изменение состояния (`write_file`, `edit_file`,
  `apply_patch`, `set_goal`, `update_plan` и подобные), не маскируются: потеря
  подтверждения сбивает модель сильнее, чем экономит токены.
- Маскировка монотонна: граница считается по номеру шага в истории, а не по
  времени. Результат, скрытый один раз, остаётся скрытым и в следующих
  запросах, поэтому префикс запроса остаётся стабильным между шагами.

## Изоляция

Общее правило для всех инструментов, читающих результат чужой работы: источник
ищется только среди данных своего чата.

- `read_run_output` принимает `run_id` и отказывает, если запуск принадлежит
  другому чату.
- Вложение ищется среди сообщений `ctx.chat.id`: `message_id` из соседнего чата
  просто отсутствует в наборе.
- `chat_history_search` со `scope=all` пересекает чаты по назначению, но
  индексирует только текст сообщений, а не содержимое вложений.

## Переполнение окна

Если запрос всё равно не помещается, ход один раз сжимает историю и повторяет
запрос. Второй отказ по окну не сжимает снова — иначе получился бы цикл
«сжать → повторить → сжать». Вместо текста провайдера модель и пользователь
получают оценку токенов, лимит окна, признак того, помогло ли сжатие, и что
делать: сократить сообщение, убрать или разделить вложение, читать файл частями.

## Настройки

| Ключ в Settings | По умолчанию | Что задаёт |
|---|---|---|
| `toolOutputForModelChars` | 60000 | Предел одного результата инструмента |
| `attachmentInlineChars` | 4000 | Превью текстового вложения в контексте |
| `attachmentMaxBytes` | 262144 | Разумный предел размера бинарного вложения |
| `logOutputDbBytes` | 1048576 | Сколько хвоста вывода запуска хранится |
| `softContextRatio` | 0.7 | Порог, после которого превью вложений ужимается |
| `contextReserveTokens` | 8000 | Резерв окна под ответ модели |
| `toolOutputKeepSteps` | 6 | Сколько последних шагов держат результаты инструментов целиком |
| `toolOutputPreviewChars` | 200 | Сколько символов старого результата остаётся в выжимке |
