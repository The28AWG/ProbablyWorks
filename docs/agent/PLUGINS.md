# Плагины

Плагин — это **скомпилированный в приложение** пакет с отключаемым функционалом.
Пользователь не устанавливает код: он только включает или выключает уже
собранные возможности. MCP — не плагин, а обычный функционал приложения.

## Архитектура

Плагин разделён на две части с разными зонами ответственности:

```text
ядро плагина (чистый Dart)
  PluginRegistry → PluginService → AgentHub / ToolExecutor
                                      ▲
                                      │ клиент и демон
                                      │
представление (Flutter)               │
  PluginUiRegistry → PluginSettingsSection → диалог настроек
```

- **Ядро** — это и есть плагин. Оно реализует `Plugin`, создаёт `PluginTool`
  и участвует в графе зависимостей и флагах `plugin.<id>.enabled`. Ядро не
  импортирует Flutter и одинаково работает в клиенте и headless-демоне.
- **Представление** — это не плагин, а дескриптор `PluginUi` с тем же
  `pluginId`. Оно даёт локализованные название, описание и экран настроек.
  Представление всегда скомпилировано в клиент, не имеет собственного флага
  включения и не входит в `PluginRegistry`.
- Связь между слоями только по `pluginId`: `PluginUiRegistry.byId` находит
  представление для ядра. Если представления нет, плагин продолжает работать,
  в настройках показывается его id, а кнопки настроек нет.
- Локализованные строки не передаются с сервера: удалённый профиль присылает
  только данные ядра, а клиент подставляет своё представление по id.

Границы импортов:

```text
plugin_api      ← только чистый Dart, без Flutter
plugin_api_ui   ← Flutter, зависит от plugin_api
*_core          ← plugin_api, без Flutter
*_ui (текущие)  ← plugin_api_ui, app_ui, локализация, своё *_core
```

## Пакеты

- `packages/plugin_api` — интерфейсы `Plugin`, `PluginTool`, `PluginHost`,
  `PluginSettings` без Flutter.
- `packages/plugin_api_ui` — интерфейс `PluginUi` и `PluginUiRegistry`. Это
  представление, а не плагин: оно привязано к `pluginId` и не влияет на
  включение инструментов.
- `packages/plugin_declarative_commands_core` — ядро фиксированных команд:
  чистый Dart, доступный клиенту и демону.
- `packages/plugin_declarative_http_core` — ядро HTTP-инструментов: чистый Dart,
  доступный клиенту и демону.
- `packages/plugin_declarative_commands` и `packages/plugin_declarative_http` —
  Flutter-представления: локализация и экраны настроек.
- Основное приложение содержит реестр ядра (`PluginRegistry`), реестр
  представлений (`PluginUiRegistry`), граф зависимостей, флаги включения и
  адаптер `PluginToolSource` к общему `ToolExecutor`.

Ядро плагина не импортирует Flutter и подключается демоном. Представление
берёт общие виджеты из `package:app_ui`, а интерфейсы — из `plugin_api_ui`.
Клиент связывает ядро и представление по `pluginId`; если представления нет,
плагин всё равно можно включать и выключать.

## Локализация

У пакета представления свои `lib/l10n/app_en.arb`, `app_ru.arb` и `l10n.yaml`.
После изменения ARB выполните в каталоге пакета:

```bash
flutter gen-l10n
```

Делегат представления регистрируется в `lib/app/locale/app_localization_delegates.dart`.
Строки в UI берутся по контексту:

```dart
final l10n = DeclarativeCommandsLocalizations.of(context);
```

Делегат регистрируется всегда, даже если плагин выключен: старые карточки
инструментов в истории должны отображаться.

## Включение и зависимости

Флаг хранится в kv как `plugin.<id>.enabled` (`yes`/`no`). Без сохранённого
флага используется `defaultEnabled`.

- При включении приложение находит все недостающие зависимости, включая
  транзитивные, и предлагает включить их вместе с плагином.
- При отключении показывает включённые зависимые плагины и отключает их вместе.
- Переключать плагины во время активного хода нельзя: набор инструментов не
  должен меняться посреди хода.
- Запрет проверяется дважды. Клиент не открывает подтверждение, если
  `AgentApi.runningChatIds` не пуст. Затем `LocalPluginApi` на агенте повторно
  проверяет активные ходы и возвращает `409 agent_busy`; это работает и для
  удалённого профиля, поэтому клиент не может обойти ограничение.
- Выключение не удаляет настройки плагина.

## Команды палитры

Плагин может добавить команды в общую палитру. Это отдельный интерфейс, чтобы
не ломать существующий `Plugin` с инструментами:

- `CommandPlugin` — `id`, локализованное название группы и
  `createCommands(PluginSettings)`;
- `PluginCommand` — `id`, `parentId`, локализованные `titles`/`keywords` и
  `run(PluginCommandHost)`;
- `PluginCommandHost` — ограниченные действия: открыть чат, новый чат,
  настройки (с необязательной категорией), уведомление. Прямого доступа к
  `BuildContext` нет.

Команды собираются в `CommandPluginRegistry` на клиенте. Плагин не получает
Flutter-зависимостей и может одинаково описывать команды для клиента и демона.
Вложенность задаётся `parentId`, в поиске команды плоские.

## API профиля

Управление плагинами идёт через `PluginApi`, а не через локальный сервис:

- `pluginSnapshot` — список ядра (`id`, `dependsOn`, `defaultEnabled`) и
  включённые id;
- `missingDependencies` / `dependents` — зависимости для подтверждения;
- `setEnabled` — включение и выключение набора id, с проверкой активных ходов;
- `settingsFor` — `PluginSettings` для экрана представления;
- `refresh` — пересборка источников инструментов после настроек.

Реализаций две, и они относятся к разным процессам, а не к разным типам
профиля в UI:

- `LocalPluginApi` живёт внутри процесса агента. Её использует GUI для
  локального профиля и демон для всех удалённых профилей.
- удалённая реализация — `RemoteAgentApi implements PluginApi`. Это тот же
  HTTP/SSE-клиент, который реализует `AgentApi`, `ChatApi`, `McpApi` и другие
  удалённые контракты; отдельного класса `RemotePluginApi` нет, чтобы не
  дублировать транспорт и кэши.

`ProfileService.pluginApiFor` выбирает реализацию:

```dart
PluginApi pluginApiFor(AgentProfile profile) =>
    profile.isLocal ? _localPluginApi : _remoteFor(profile);
```

Названия, описания и экраны настроек остаются в `PluginUiRegistry` клиента и
подбираются по `pluginId`.

## Инструменты

Плагин возвращает `PluginTool`. Приложение адаптирует его в `ToolSource`:

- имя становится `plugin_<pluginId>_<toolName>`;
- вызов проходит общий `PolicyEngine` и подтверждение;
- `PluginHost.runCommand` запускает executable и args без shell-интерполяции;
- если инструмент может менять Host, ход помечается неоткатываемым.

Модель не может подменить executable или фиксированные аргументы команды.

## HTTP-инструменты

Плагин `declarative_http` хранит инструменты в том же JSON-формате:

```json
{
  "id": "weather",
  "title": "Weather",
  "description": "Current weather",
  "method": "GET",
  "url": "https://api.example.com/weather?city={{city}}",
  "headers": {"Authorization": "Bearer ${secret:weather}"},
  "inputSchema": {
    "type": "object",
    "properties": {"city": {"type": "string"}},
    "required": ["city"]
  },
  "timeoutSeconds": 30,
  "maxResponseChars": 20000,
  "responseFormat": "json",
  "jsonPath": "$.current.temperature"
}
```

- `{{name}}` подставляется из аргументов: в URL — с percent-encoding,
  в заголовках и теле — как строка.
- `${secret:name}` в заголовках разрешается приложением через `SecretStore`.
- `responseFormat`: `text`, `json` или `html`.
- Для `json` можно указать `jsonPath`, для `html` — `htmlSelector`.
- Ответ обрезается до `maxResponseChars`, ошибки HTTP возвращаются как
  `isError` с кодом и телом.

## Настройки

Настройки плагина хранятся в kv как JSON по ключу `pluginSettings.<id>`.
`PluginSettings.save` записывает JSON и пересобирает инструменты плагина.

Экран настроек плагина живёт в его пакете и получает `PluginSettings` от
приложения. После закрытия экрана приложение ещё раз обновляет источники
инструментов.

## Новый плагин

1. Создать в `packages/` пакет ядра `*_core` без Flutter и добавить его в
   `workspace` и зависимости клиента и демона.
2. Реализовать в ядре `Plugin` и, при необходимости, `PluginTool`.
3. Создать Flutter-пакет представления, если нужны своя локализация или экран
   настроек. Он зависит от `plugin_api_ui` и пакета ядра.
4. Добавить ARB, `l10n.yaml` и сгенерировать локализацию в пакете представления.
5. Зарегистрировать делегат в `app_localization_delegates.dart`.
6. Добавить ядро в `PluginRegistry` клиента и демона.
7. Добавить `PluginUi` в `PluginUiRegistry` клиента, если нужен экран настроек.
8. Покрыть ядро тестами создания инструментов и графа зависимостей.

### Команды палитры и offline

`PluginCommand` по умолчанию считается серверным и скрывается при offline.
Если команда умеет работать без агента, плагин явно ставит
`requiresBackend: false`.
