# Семантический поиск: варианты и перспективы

**Статус:** отложено. В PW-018 остаются память проекта и надёжный FTS-поиск;
семантический поиск вынесен в отдельное решение.

**Связанные задачи:** PW-018 (долговременная память и поиск), PW-020
(глобальный поиск в UI).

## 1. Проблема

Сейчас поиск по истории устроен на FTS5. Он хорошо находит точные слова и
идентификаторы, но не помогает, когда решение сформулировано другими словами:

- в чате написано «каталог моделей грузится через ModelCatalogService»;
- запрос: «где мы ходим в OpenRouter за списком моделей»;
- FTS может не найти совпадений, потому что общих слов нет.

Семантический поиск решает эту задачу: текст и запрос переводятся в векторы
(embeddings), а поиск идёт по близости смысла. Это не замена FTS, а дополнение:
точные имена, команды и пути по-прежнему лучше искать обычным способом.

## 2. Что входит в решение

Даже минимальный семантический поиск — это не один вызов модели, а цепочка:

1. **Источники.** Сообщения чатов, файлы проекта, возможно summary и память.
2. **Чанкинг.** Разбиение текста на фрагменты с перекрытием и метаданными
   (чат, сообщение, путь, строки).
3. **Embedding-модель.** Превращает текст в вектор.
4. **Хранилище векторов.** Таблица или индекс с поддержкой поиска по близости.
5. **Инкрементальная индексация.** Добавление, обновление и удаление векторов
   вместе с сообщениями и файлами.
6. **Retrieval.** Запрос → вектор → top-k фрагментов.
7. **Интеграция с агентом.** Найденное передаётся модели как недоверенные
   данные, с цитатами и лимитом токенов.

RAG — следующий шаг: не просто показать фрагменты, а собрать из них контекст
для ответа. Поэтому RAG и семантический поиск удобно делать поэтапно.

## 3. Пути решения

### A. Удалённый embedding-провайдер

Использовать embedding-модель через HTTP API: OpenRouter, OpenAI-совместимый
сервис или специализированный провайдер.

**Как устроено.**

- В `pw_agent` появляется порт `EmbeddingProvider`.
- Реализация ходит в API и возвращает векторы.
- Векторы хранятся локально, в SQLite.
- Индексация сообщений и файлов идёт в фоне.

**Что меняется.**

- Новый порт и адаптер.
- Таблица векторов и миграция схемы.
- Очередь индексации.
- Настройка embedding-модели.
- API/SSE для прогресса индексации, если нужен удалённый клиент.

**Плюсы.**

- Самый маленький объём работ.
- Нет нативных библиотек и lifecycle-модели.
- Работает одинаково в embedded и daemon-режиме.
- Не нужны гигабайты RAM/диска.
- Легко добавить RAG по тем же векторам.

**Минусы.**

- Текст чатов и файлов уходит внешнему провайдеру.
- Нужен ключ и оплата embeddings.
- Для приватных проектов и кода это может быть неприемлемо.
- Качество и размерность зависят от провайдера.

**Перспективы.**

- Быстрый semantic search без локальных моделей.
- RAG по истории и файлам.
- Гибридный поиск FTS + semantic.
- Возможность позже заменить провайдера на локальный без смены схемы.

**Оценка:** средняя задача, но заметно меньше, чем локальный чат-провайдер.

### B. Локальные embeddings через llamadart

Использовать `llamadart` только для embedding-модели. Чат остаётся на
OpenRouter или другом текущем провайдере.

**Как устроено.**

- Новый пакет `pw_local_llm` (или аналогичный) зависит от `llamadart`.
- Внутри — один embedding-движок и одна модель, например EmbeddingGemma-2,
  bge-m3 или e5.
- `pw_agent` получает `EmbeddingProvider`, реализация — локальная.
- Векторы хранятся в SQLite; поиск — косинус в Dart или `sqlite-vec`.

**Что меняется.**

- Пакет с локальной реализацией.
- Менеджер модели: скачивание, кэш, загрузка, выгрузка, ошибки.
- Настройка embedding-модели и пути к файлу.
- Индексация и хранение векторов.
- Упаковка нативных библиотек в daemon и embedded GUI.
- Dispose при выходе и hot restart.

**Плюсы.**

- Данные не уходят наружу.
- Нет оплаты за embeddings.
- Один раз загруженная модель работает офлайн.
- Это фундамент для RAG без обязательного локального чата.
- Значительно меньше работы, чем полный локальный LLM-провайдер.

**Минусы.**

- Появляются нативные библиотеки и платформенная упаковка.
- Нужно управлять жизненным циклом хотя бы одного движка.
- Модель занимает сотни мегабайт.
- Скорость на CPU ниже, чем у API.
- Нужны проверки платформ и памяти.

**Перспективы.**

- Локальный semantic search.
- RAG по проекту.
- Позже можно добавить локальную чат-модель на той же инфраструктуре.
- Хороший компромисс между приватностью и объёмом работ.

**Оценка:** средняя/крупная задача. Это минимальный разумный путь, если
приватность важна, а локальный чат пока не нужен.

### C. Полный локальный LLM-провайдер через llamadart

Добавить не только embeddings, но и локальные чат-модели: выбор модели,
загрузка, стриминг, tool calling, память, заголовки, субагенты.

**Как устроено.**

- Реестр провайдеров: OpenRouter и local.
- Локальные id вида `local:qwen3-4b`.
- `LocalModelManager` владеет движками и сериализует загрузку/выгрузку.
- Настройки: файл модели, контекст, GPU layers, threads, auto-unload.
- API/UI для скачивания, прогресса, статуса и ошибок.
- Embeddings — отдельный движок или отдельная модель.

**Что меняется.**

- `LlmProvider` перестаёт быть одним синглтоном.
- Каталог моделей объединяет OpenRouter и локальные модели.
- `SavedModel`, `LlmModelInfo` и настройки получают провайдера.
- Выбор модели в UI группируется по провайдерам.
- `ChatSession`, `ContextCompactor`, `ChatTitle`, `ProjectMemoryService`
  должны корректно работать с локальными моделями.
- Нужны проверки tool calling и контекста до выбора модели.
- Нужна упаковка нативных runtime-ов в daemon и GUI.

**Плюсы.**

- Полностью локальный агент.
- Нет обязательной зависимости от OpenRouter.
- Офлайн-работа.
- Единая инфраструктура для чата, embeddings и RAG.
- Возможность тонкой настройки моделей под железо.

**Минусы.**

- Это отдельный крупный эпик.
- Локальные модели заметно хуже в tool calling и длинном контексте.
- Несколько гигабайт RAM/VRAM и диска.
- Сложный lifecycle: загрузка, выгрузка, конкуренция чата и embeddings.
- Нативная упаковка и подпись на macOS.
- Много платформенного тестирования.
- Качество модели зависит от железа.

**Перспективы.**

- Локальный чат, память, embeddings и RAG на одной базе.
- Приватный режим для чувствительных проектов.
- Независимость от внешних API.
- Но ценность и риски здесь уже не про поиск, а про весь продукт.

**Оценка:** крупный эпик, сравнимый с PW-017 по объёму.

### D. Внешний локальный LLM-сервер

Не встраивать модель в приложение, а подключиться к уже запущенному серверу:
Ollama, LM Studio, llama.cpp server или vLLM.

**Как устроено.**

- Провайдер — обычный HTTP-адаптер.
- Пользователь сам запускает сервер и скачивает модель.
- Приложение получает список моделей, чат и embeddings по API.

**Что меняется.**

- Настройка URL и, возможно, токена.
- Каталог моделей от сервера.
- Проверка доступности и статуса.
- Никакого нативного lifecycle в приложении.

**Плюсы.**

- Гораздо меньше работы, чем вариант C.
- Локальные модели и приватность.
- Пользователь сам управляет памятью, GPU и моделями.
- Нет нативной упаковки.
- Подходит и для чата, и для embeddings, и для RAG.

**Минусы.**

- Нужен внешний сервер и его настройка.
- Не «из коробки» для обычного пользователя.
- Качество и совместимость зависят от сервера.
- Нужен отдельный endpoint для embeddings.
- Для удалённого профиля нужен доступ к серверу.

**Перспективы.**

- Быстрый путь к локальному чату и RAG без встраивания llama.cpp.
- Хороший вариант для продвинутых пользователей.
- Можно позже заменить на встроенный провайдер.

**Оценка:** малая/средняя задача, если не нужен «один клик».

### E. Гибридный поиск FTS + semantic + rerank

Это не отдельный источник embeddings, а способ использования уже полученных
векторов.

**Как устроено.**

- FTS ищет точные совпадения.
- Semantic ищет по смыслу.
- Результаты объединяются, при необходимости переранжируются
  cross-encoder-моделью.
- В prompt попадают top-k фрагментов с цитатами.

**Плюсы.**

- Лучшее качество, чем у каждого метода по отдельности.
- Точные идентификаторы не теряются.
- Смысловые совпадения добавляются.
- Rerank можно добавить позже.

**Минусы.**

- Нужны обе инфраструктуры.
- Сложнее настройка весов и лимитов.
- Rerank добавляет задержку и ещё одну модель.

**Перспективы.**

- Основной режим поиска для агента.
- Основа RAG.
- Прозрачные цитаты и контроль контекста.

**Оценка:** надстройка поверх A/B/C/D, а не самостоятельный первый шаг.

## 4. Сравнение

| Путь | Приватность | Стоимость | Lifecycle | Объём | Что открывает |
| --- | --- | --- | --- | --- | --- |
| A. Remote embeddings | низкая | оплата API | нет | средний | semantic search, RAG |
| B. Local embeddings | высокая | железо | один движок | средний/крупный | semantic search, RAG, база для local |
| C. Full local provider | высокая | железо | много движков | крупный | локальный чат + RAG |
| D. External LLM server | высокая | железо | внешний | малый/средний | локальный чат + RAG |
| E. Hybrid/rerank | зависит | зависит | зависит | небольшой поверх | лучшее качество поиска |

## 5. Почему не плагин

Плагинный API сейчас даёт только инструменты:

```dart
abstract interface class Plugin {
  Future<List<PluginTool>> createTools(PluginSettings settings);
}
```

В нём нет:

- регистрации `LlmProvider`;
- embeddings;
- каталога моделей;
- lifecycle движка;
- настроек провайдера;
- UI и API для моделей.

Локальный провайдер — это часть ядра и инфраструктуры профиля, а не плагин.
Плагином можно сделать, например, отдельный инструмент поиска по внешнему
сервису, но не управление локальными моделями.

## 6. Рекомендуемая последовательность

Если возвращаемся к задаче:

1. **Spike.** Собрать daemon с `llamadart`, загрузить маленькую GGUF-модель,
   получить embedding, проверить `dart build cli`, упаковку и dispose.
2. **Embedding-only.** Порт `EmbeddingProvider`, локальная модель, таблица
   векторов, индексация сообщений, semantic search в инструменте.
3. **Hybrid.** Добавить FTS + semantic и лимиты контекста.
4. **RAG по файлам.** Чанкинг, ignore-правила, индексация, цитаты.
5. **Local chat provider.** Только если после предыдущих шагов действительно
   нужен локальный чат, а не только поиск.

Для варианта D шаги 1–4 можно сделать без нативной упаковки: сервер уже
запущен, приложение только ходит по HTTP.

## 7. Когда возвращаемся

Задача становится актуальной, если:

- появится требование искать по смыслу, а не по словам;
- появится требование приватного RAG по коду и чатам;
- будет выбран путь с внешним локальным сервером или локальной
  embedding-моделью;
- появится ресурс на lifecycle и платформенную упаковку.

До этого FTS + память проекта закрывают практические сценарии.

## 8. Открытые вопросы

- Нужен ли semantic search по файлам или только по истории чатов?
- Допустимо ли отправлять код внешнему embedding-провайдеру?
- Есть ли целевое железо для локальной модели?
- Нужен ли локальный чат или достаточно embeddings?
- Готовы ли мы поддерживать нативную упаковку на всех платформах?
- Какой бюджет по задержке и памяти считается приемлемым?
