# Безопасность ProbablyWorks

Документ описывает модель угроз и требования к безопасности, в первую очередь
для будущего headless-демона и удалённого API. Это не описание готовой
реализации, а граница между тем, что мы действительно защищаем, и тем, что пока
является доверием к агенту.

## 1. Главный тезис

**Шифрование секретов защищает диск и других пользователей, но не защищает от
агента, который работает под той же учётной записью и имеет произвольный
`run_command` или `read_file`.**

Если агент может выполнять команды и читать файлы с правами пользователя, он
может:

- вызвать `secret-tool`, keyring или другой доступный менеджер секретов;
- прочитать `.env`, конфиги, SSH-ключи, файлы приложения;
- посмотреть переменные окружения дочерних процессов;
- прочитать зашифрованный файл, если мастер-ключ лежит рядом;
- попросить MCP-сервер или плагин сделать это за него;
- получить команду через prompt injection из файла, веб-страницы или вывода
  инструмента.

`PolicyEngine` — это защита от опасных действий и способ показать пользователю
намерения агента. Это **не граница безопасности** и не sandbox. Запрет `sudo`
или отдельных команд не мешает `cat`, `base64`, другому интерпретатору или
обфускации.

Поэтому если не применяются меры изоляции, мы обязаны явно говорить:
**агент доверяется полностью, как доверяют собственной учётной записи.**

## 2. Что считается компрометацией

Для целей этого документа компрометацией считаются:

- агент получил секрет, который не должен был видеть;
- агент смог отправить данные наружу без разрешения пользователя;
- агент вышел за пределы workspace;
- агент получил права выше, чем у пользователя, запустившего приложение;
- удалённый клиент API выполнил действие без авторизации;
- MCP-сервер или плагин получил доступ к секретам или keyring;
- prompt injection заставил агента выполнить опасное действие;
- секреты попали в логи, БД, контекст модели или сообщения об ошибках.

## 3. MVP для headless-режима

Сначала нужен минимальный, честно описанный уровень защиты. Это не полноценная
изоляция агента, а «фиговый листочек», который закрывает самые грубые ошибки
развёртывания.

### 3.1. Сетевой доступ

- API по умолчанию слушает только `127.0.0.1`/`::1`.
- Удалённый bind (`0.0.0.0`, внешний интерфейс) только явным переключателем.
- По умолчанию нет CORS для браузерных клиентов.
- Для удалённого доступа рекомендуется SSH-туннель, VPN или reverse proxy с TLS.
- Встроенный TLS не обязателен для MVP, но и удалённый HTTP без TLS не должен
  считаться безопасным режимом.

### 3.2. Аутентификация API

- При первом запуске генерируется случайный токен доступа.
- Токен хранится только в `SecretStore`, не в SQLite и не в логах.
- На desktop демон использует OS-keyring: Secret Service на Linux, Keychain
  на macOS и Credential Manager на Windows. Без доступного keyring остаётся
  файл `0600` как fallback.
- Все API-запросы, кроме минимального health-check, требуют
  `Authorization: Bearer <token>`.
- Сравнение токена — constant-time.
- Токен можно перевыпустить; старый токен сразу перестаёт работать.
- UI показывает токен только по явному действию пользователя.

### 3.3. Секреты и данные

- Секреты не попадают в БД, логи, сообщения об ошибках и контекст модели.
- `SecretStore` принадлежит привилегированной части приложения.
- Агентские инструменты не получают сырые секреты через аргументы или
  переменные окружения.
- `Redactor` применяется к выводу инструментов и ошибкам.
- Файлы БД, логов и конфигурации имеют права только для владельца: каталоги
  `0700`, файлы `0600`. Приложение выставляет режим сразу после создания;
  для уже существующих файлов он не повторяется, чтобы не скрывать изменения,
  сделанные извне.
- На Linux и macOS используется `chmod`; на macOS перед ним выполняется
  `chmod -N`, чтобы снять унаследованные ACL. На Windows права задаются через
  `icacls`: наследование отключается, полный доступ остаётся только текущему
  пользователю.
- На Android и iOS режимы не меняются: внутренний каталог приложения и так
  закрыт песочницей ОС и отдельным UID, а на iOS порождать процессы нельзя.
- Известные файлы верхнего уровня (БД, `mcp.json`, lock) и корневые каталоги
  данных, созданные старыми версиями с режимом из umask, один раз
  нормализуются при первом запуске новой версии. Дальнейшие отклонения от
  `0700`/`0600` считаются признаком вмешательства.

### 3.4. Ограничения API

- Лимит размера запроса и ответа.
- Таймауты на все операции.
- Ограничение количества одновременных запросов.
- Аудит: кто, когда и какое действие запросил.
- Отдельный журнал ошибок авторизации.

### 3.5. Владение базой

- Один процесс-хозяин владеет SQLite.
- Второй экземпляр не открывает ту же базу на запись.
- Для daemon это означает, что GUI не должен ходить в БД напрямую.
- При падении процесса незавершённые задачи восстанавливаются по журналу и
  существующему recovery-механизму.

### 3.6. Честное предупреждение

В UI и документации должно быть явно написано:

> Headless API даёт удалённое управление агентом. Если агент имеет доступ к
> shell, это фактически удалённое выполнение команд. Не выставляйте API в сеть
> без авторизации, TLS и понимания рисков.

MVP **не защищает от самого агента**. Он защищает от случайного открытия API,
простого перебора, утечки секретов в логи и одновременной записи в БД.

## 4. Что нужно разработать для защиты от агента

Эти меры зависят от ОС и должны внедряться поэтапно. Пока они не внедрены,
действует правило полного доверия агенту.

### 4.1. Разделение привилегий

- Демон/control plane владеет `SecretStore`, БД и API.
- Агентские команды выполняются отдельным непривилегированным процессом или
  пользователем.
- Этот процесс не имеет доступа к keyring, конфигу демона, мастер-ключу и
  сокету управления.
- Рабочая папка проекта — единственный разрешённый общий ресурс.

Linux:

- отдельный пользователь `probablyworks-agent`;
- systemd hardening: `NoNewPrivileges`, `ProtectSystem`, `ProtectHome`,
  `PrivateTmp`, `PrivateDevices`, ограничение D-Bus;
- при необходимости — `bubblewrap`, `nsjail` или `firejail`.

macOS:

- отдельный пользователь или App Sandbox;
- LaunchAgent для пользовательской сессии, не системный демон без крайней
  необходимости;
- Keychain доступен только control plane.

Windows:

- отдельная учётная запись службы;
- AppContainer/Job Object для дочерних процессов;
- DPAPI/Credential Manager только в control plane.

### 4.2. Ограничение области видимости

- Агент видит только workspace проекта, а не весь домашний каталог.
- Скрыты `~/.config`, `~/.ssh`, `~/.local`, keyring-сокеты, файлы БД,
  мастер-ключи и логи.
- Пути вне workspace недоступны на уровне ОС, а не только через policy.
- Симлинки и монтирования не позволяют выйти за границу.

### 4.3. Ограничение инструментов

- Режим без произвольного shell: только типизированные операции.
- `run_command` либо отключён, либо ограничен allowlist-командами.
- `read_file`/`write_file` ограничены workspace.
- MCP-серверы и плагины запускаются в отдельных процессах с теми же
  ограничениями.
- Инструменты, которым нужен секрет, не получают его значение, а вызывают
  привилегированное действие.

### 4.4. Ограничение прав

- Запрет повышения привилегий на уровне ОС.
- Нет доступа к D-Bus/keyring, если он не нужен.
- Нет доступа к сетевым сокетам демона.
- seccomp/AppArmor/landlock на Linux, sandbox на macOS, AppContainer на Windows.
- Лимиты CPU, памяти, числа процессов и диска.

### 4.5. Secret broker

Агент не должен уметь читать секрет. Он должен уметь только попросить
выполнить разрешённое действие:

- HTTP-запрос с подстановкой `Authorization` на стороне прокси;
- запуск фиксированной команды с credential helper;
- использование SSH-ключа без раскрытия ключа агенту.

Broker проверяет:

- какое действие разрешено;
- к какому секрету можно обратиться;
- какой домен/хост допустим;
- какой пользователь и чат инициировали действие.

Сырое значение секрета не возвращается агенту и не попадает в контекст модели.

### 4.6. Чтение файлов

- `read_file`, `grep`, `glob`, `stat_path` и `list_dir` проверяют путь до
  обращения к Host.
- Чувствительные пути и файлы требуют подтверждения даже в YOLO:
  `~/.ssh`, облачные credentials, keychains, `.env` и token-файлы.
- Чтение вне workspace в режиме Ask требует подтверждения. В YOLO обычные
  пути вне workspace разрешены, но чувствительные по-прежнему спрашивают.
- Это policy, а не sandbox: `run_command` может прочитать те же данные, если
  команда прошла командную политику. Полная изоляция описана в L2.

### 4.7. Сетевой egress

- По умолчанию исходящая сеть ограничена.
- HTTP/HTTPS — через прокси с allowlist доменов.
- Запрещены localhost, приватные подсети, metadata-сервисы облака и
  нестандартные порты без явного разрешения.
- DNS-запросы также должны проходить через контролируемый резолвер.
- Это нужно, чтобы prompt injection не мог отправить секреты наружу.

### 4.8. Удалённый API

- Токен + TLS обязательны для любого не-loopback доступа.
- Ротация токена.
- Ограничение частоты запросов.
- Аудит действий и ошибок авторизации.
- Отдельный API-пользователь/роль, если появится многопользовательский режим.
- Запрет опасных действий по умолчанию; подтверждения не должны отключаться
  удалённо без явного действия пользователя.

## 5. Уровни зрелости безопасности

### L0. MVP, текущий «фиговый листочек»

- loopback + токен;
- секреты не в БД/логах;
- redaction;
- ограничения API;
- один владелец БД;
- предупреждение в UI.

Что защищено: диск, случайный доступ к API, другие пользователи ОС.
Что не защищено: сам агент, prompt injection, malicious MCP/plugin, root.

### L1. Изолированный worker

- агентские команды — отдельный пользователь/процесс;
- workspace-only;
- keyring и конфиг демона недоступны;
- политика и лимиты ресурсов.

Что защищено: агент не читает секреты и не выходит за workspace
средствами обычного shell.
Остаётся: сетевая эксфильтрация, platform-specific обходы.

### L2. Sandbox + secret broker + egress proxy

- полноценная песочница;
- секреты не покидают control plane;
- сеть только через allowlist;
- MCP/плагины изолированы.

Что защищено: большинство сценариев prompt injection и кражи секретов.
Остаётся: уязвимости ядра/песочницы, root.

### L3. Одноразовая VM/контейнер на задачу

- агент вообще не имеет доступа к хосту;
- только явно смонтированный workspace;
- сеть через прокси;
- уничтожение среды после задачи.

Это максимальный уровень, но дорогой по ресурсам и сложный в UX.

## 6. Матрица ОС

| Возможность | Linux | macOS | Windows |
|---|---|---|---|
| Keyring/секреты | Secret Service/libsecret, systemd-creds, TPM2 | Keychain, Secure Enclave | DPAPI, Credential Manager |
| Изоляция | namespaces, bwrap, nsjail, seccomp, Landlock, systemd hardening | App Sandbox, отдельный пользователь | AppContainer, Job Object, отдельная служба |
| Права | отдельный UID, capabilities, ACL | sandbox entitlements, отдельный пользователь | отдельная учётная запись, ACL |
| Сеть | netns, proxy, nftables | sandbox network rules, proxy | AppContainer network, proxy |
| Headless keyring | требует разблокированного keyring или TPM/systemd-creds | требует пользовательской сессии/Keychain | DPAPI работает без GUI |

## 7. Чек-лист MVP

- [x] API слушает только loopback по умолчанию.
- [x] Есть токен доступа, он хранится в `SecretStore`.
- [x] Все опасные endpoint'ы требуют авторизацию.
- [ ] Нет секретов в БД, логах, ошибках и контексте модели.
- [ ] `Redactor` применяется к выводам и ошибкам.
- [x] Удалённый bind выключен по умолчанию.
- [ ] В UI есть предупреждение о рисках headless API: API живёт в демоне, предупреждение — в DAEMON.md.
- [x] Есть лимит размера запроса и таймауты; отдельный аудит API пока не ведётся.
- [ ] Один процесс владеет БД.
- [ ] Документация честно говорит: без изоляции агент доверяется полностью.

## 8. Явное ограничение ответственности

Если меры L1–L3 не внедрены, приложение **не должно заявлять**, что оно
защищает секреты от агента. Оно защищает их от кражи диска, случайного доступа
и других пользователей, но не от кода, который выполняется с теми же правами.

Для локального агента с полноценным shell это означает доверие уровня
«пользователь разрешил программе работать от своего имени». Для headless-демона
с удалённым API это доверие уровня «удалённое выполнение команд».

## 9. Самотест окружения

В настройках есть детерминированный аудит окружения. Он проверяет:

- режим работы и права процесса;
- backend `SecretStore`;
- отклонение прав БД, логов и `mcp.json` от ожидаемых `0600`/`0700`;
- переменные окружения, похожие на секреты;
- политику `yolo` и пустой denylist;
- включённые плагины и MCP-серверы;
- состояние headless API;
- наличие single-instance lock.

Проверка прав зависит от платформы. На Linux и macOS сравниваются
POSIX-режимы с ожидаемыми; если права ослаблены внутри каталога `0700`, до
файла всё равно нельзя дойти, поэтому такая находка остаётся предупреждением.
Критичной она становится только когда файл или каталог реально доступен
другому пользователю. На Windows ACL пока не проверяются, поэтому аудит честно
пишет «права не проверены». На Android и iOS режимы не сравниваются: граница
там — UID и песочница ОС, и аудит сообщает об этом отдельной находкой.

Аудит не запускает команды, не ходит в сеть и не читает значения секретов.
Его вердикт — `unsafe`, `baseline`, `unknown` или `isolated`. В GUI-режиме
максимум — `baseline`: он означает, что MVP-проверки пройдены, но агент
по-прежнему полностью доверен.

Ядро аудита живёт в `pw_agent` и работает и в GUI, и в демоне. Удалённый
профиль получает отчёт через `GET /security/audit`: проверяются права файлов,
переменные окружения и включённые инструменты на машине сервера, а не на
клиенте. Для демона режим отчёта — `headless`.

## 10. Вне области рассмотрения

- compromised OS, root/admin, kernel exploits;
- физический доступ к машине;
- malicious compiled plugin, которому дали те же права, что и приложению;
- утечки через сторонние сервисы, которым пользователь сам отправил данные;
- защита от пользователя, который намеренно хочет выполнить опасное действие.
