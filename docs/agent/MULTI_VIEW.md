# Несколько клиентов и точек отображения

Документ описывает модель «один агент — много окон и устройств»: рукопожатие
клиента, временные сессии, присутствие и правила синхронизации состояния.
Это не многопользовательский режим: пользователь один, а клиентов может быть
несколько.

## Термины

| Термин | Что означает |
|---|---|
| **AgentProfile** | Клиентская запись «куда звонить»: URL демона и токен. На сервере такой сущности нет. |
| **instanceId** | Идентификатор запущенного экземпляра сервера. Новый процесс — новый `instanceId`. Не переживает перезапуск и нужен, чтобы отличить «тот же самый экземпляр» от «сервер перезапустился». |
| **sessionId** | Временный идентификатор клиента, который выдаёт сервер при рукопожатии. Живёт до TTL или явного закрытия. Не является токеном авторизации. |
| **resumeSecret** | Секрет продолжения сессии. Сервер выдаёт его вместе с `sessionId`, клиент хранит рядом и присылает только в рукопожатии. В список сессий не попадает: одного `sessionId` недостаточно, чтобы продолжить чужое представление. |
| **clientId** | Стабильный id установки: UUID, который клиент создаёт один раз и хранит между запусками и обновлениями. На web лежит в `localStorage`, на native — в клиентских настройках приложения. Это не глобальный идентификатор устройства и не граница безопасности: очистка данных или новый профиль браузера создаёт новый `clientId`. |
| **deviceId** | Отпечаток модели клиента: короткий SHA-256 от `X-Client-*` (приложение, пакет, версия, сборка, платформа). Меняется при обновлении приложения и может совпасть у двух одинаково описанных машин. Остаётся запасным ключом группировки для старых клиентов и для журнала. |
| **Bearer-токен** | Секрет API, один на экземпляр сервера. Он не является пользователем, не создаёт учётные записи и не привязывает сессии к пользователям. Сессия не заменяет и не ослабляет его. |

Смысл разделения:

- `AgentProfile` отвечает на вопрос **куда** подключаться;
- `instanceId` — **какой запуск** сервера отвечает;
- `sessionId` — **какой клиент** сейчас работает;
- `clientId` — **какая установка** и, следовательно, какое устройство;
- `deviceId` — отпечаток описания клиента для старых клиентов и журнала.

## Что реализовано

- Сервер выдаёт `sessionId` при рукопожатии, хранит сессии в памяти и
  проверяет `X-Client-Session` на всех запросах, кроме `/health`,
  `/client/probe` и `/client/handshake`.
- Вместе с `sessionId` сервер выдаёт `resumeSecret`, а клиент хранит его
  рядом. Продолжить сессию по одному `previousSessionId` нельзя: нужен
  секрет, выданный этой же сессии, и совпадающий `clientId`, если обе стороны
  его прислали. Список сессий отдаёт короткий fingerprint вместо сырого id и
  не раскрывает секрет.
- `instanceId` создаётся при старте `ApiServer` и отдаётся в `/health` и в
  ответе рукопожатия. Перезапуск сервера меняет `instanceId`; старые сессии
  после него недействительны.
- `clientId` — стабильный UUID установки, который клиент создаёт один раз и
  хранит между запусками. Он не вычисляется из версии или платформы:
  обновление приложения меняет атрибуты, но не устройство. `deviceId`
  по-прежнему вычисляется сервером из заголовков `X-Client-*` как короткий
  SHA-256 и остаётся запасным ключом группировки и полем журнала.
- Список экранов группирует вкладки и окна по `clientId`, а для старых
  клиентов — по `deviceId`. Устройство показывает число подключений и
  раскрывает свои вкладки.
- У клиента есть `ClientSessionStore` и `ClientSessionChannel`: память для
  desktop/mobile, `sessionStorage` и `BroadcastChannel` для web.
- `RemoteAgentApi` делает рукопожатие один раз на профиль, повторяет запрос
  после `410 session_expired`/`400 session_required`, шлёт heartbeat и
  заголовок сессии в SSE.
- Состояние между клиентами синхронизируется событиями и ревизиями:
  - закрытие подтверждений, вопросов и выбора откатов файлов;
  - полная очередь с `queueRevision`;
  - настройки и каталог моделей;
  - метаданные открытого чата и его удаление отдельным событием
    `chatDeleted` с каскадом субагентов;
  - снимок живого хода `turnSnapshot`;
  - независимые ревизии черновика и правок сообщений;
  - идемпотентная отправка по `clientMessageId`;
  - точечный `PATCH` метаданных чата с `expectedRevision`;
  - порядок присутствия по `presenceRevision` и список клиентских сессий.
- Обрыв SSE считается потерей связи, даже если поток закрылся без ошибки:
  статус остаётся `offline` до нового потока, а снимки перечитываются при
  обрыве и ещё раз после переподключения.
- В `docs/agent/DAEMON.md` обновлён контракт API и список SSE-событий.

Синхронизация не делает из одного агента многопользовательский сервер:
пользователь один, а клиентов/окон может быть несколько.

## Рукопожатие

Запрос:

```http
POST /api/v1/client/handshake
Authorization: Bearer <token>
Content-Type: application/json
X-Client-Id: <uuid установки>
X-Client-App: ProbablyWorks
X-Client-Version: 1.2.3
X-Client-Build: 42
X-Client-Platform: linux

{"protocol": 1, "previousSessionId": "...", "previousSessionSecret": "..."}
```

`previousSessionId` и `previousSessionSecret` необязательны. Это подсказка
для непрерывности после перезагрузки вкладки или повторного подключения, а не
доказательство. Запрос уже авторизован Bearer-токеном сервера. Сессия
переиспользуется, только если она ещё жива, секрет совпадает, а `clientId`
(если он есть у обеих сторон) тот же. Иначе создаётся новая сессия; живая
чужая при этом не удаляется. Если сервер не знает старый id (истёк TTL,
перезапуск, другой экземпляр), он тоже создаёт новую сессию.

Ответ:

```json
{
  "sessionId": "…",
  "resumeSecret": "…",
  "instanceId": "…",
  "deviceId": "9f1c2d3e4a5b6c7d",
  "clientId": "8a2f…",
  "protocol": 1,
  "expiresAt": "2026-11-24T12:00:00.000Z",
  "heartbeatIntervalMs": 20000,
  "presenceRevision": 0
}
```

`resumeSecret` клиент хранит только у себя и присылает лишь в следующем
рукопожатии. `deviceId` — отпечаток, `clientId` — стабильный ключ устройства.

Дальше клиент обязан передавать сессию:

```http
X-Client-Session: <sessionId>
```

на всех запросах, включая `GET /api/v1/events` и обычные REST-вызовы.

Исключения:

- `GET /api/v1/health` — открыт и не требует сессии;
- `GET /api/v1/client/probe` — требует Bearer, но не сессию; сессию не создаёт;
- `POST /api/v1/client/handshake` — единственный маршрут, который сессию
  создаёт;
- статические файлы web-сборки — не API.

Ошибки:

- `400 session_required` — заголовка нет, а сервер требует сессию;
  исключения — `/health`, `/client/probe` и `/client/handshake`;
- `410 session_expired` — сессия неизвестна или истекла; клиент делает новое
  рукопожатие и один раз повторяет запрос.

Проверка сессии выполняется до маршрута. Поэтому `410` гарантирует, что
изменяющий запрос не был выполнен, и повтор безопасен. Для сетевых таймаутов
это не так: отправка сообщения несёт `clientMessageId` (см. раздел 9), и
повтор с тем же значением в том же чате не создаёт второе сообщение.
Повторное сохранение черновика, версия которого уже лежит на сервере,
считается успешной записью, а не конфликтом.

## Жизненный цикл сессии

- TTL по умолчанию — 60 секунд, heartbeat — каждые 20 секунд. Значения
  приходят в ответе рукопожатия, чтобы клиент не зашивал их в код.
- Любой запрос с валидной сессией продлевает `lastSeenAt`.
- Открытый SSE тоже продлевает сессию: сервер обновляет `lastSeenAt`, когда
  пишет в поток ping. Браузер в фоновой вкладке затормаживает таймеры клиента,
  и heartbeat может не успеть до TTL. Без этого экран «пропадал» из
  присутствия и возвращался только при переключении вкладки.
- Закрытие вкладки определяется двумя путями. Web-клиент на `pagehide`
  отправляет keepalive `PUT /client/session` с `{"closing": true}`. Сервер
  также ставит отметку закрытия, когда у сессии закрылось последнее
  SSE-соединение. Это покрывает браузеры и случаи, где `pagehide` не сработал.
- Отметка закрытия не удаляет сессию сразу: есть пауза `closeGrace` (5 секунд).
  Любой обычный запрос, heartbeat, рукопожатие или новое SSE снимают отметку.
  Поэтому reload и короткий обрыв связи переиспользуют сессию, а закрытая
  вкладка исчезает из списка через несколько секунд, не дожидаясь TTL.
  SSE-ping отметку не снимает: поток может ещё жить, пока браузер выгружает
  страницу.
- После изменения присутствия клиент перечитывает список сессий. Это убирает
  устаревший снимок, в котором текущего экрана уже нет. Параллельные чтения
  не применяют более старый ответ: иначе он мог прийти позже и перезаписать
  свежий список, и экраны показывали бы разное число клиентов.
- Присутствие упорядочено монотонной `presenceRevision`. Клиент отправляет не
  больше одного запроса одновременно и назначает растущую ревизию каждой
  отправке: если изменение пришло во время отправки, уходит последнее состояние,
  а не накопленная очередь. Сервер применяет состояние, лишь когда ревизия
  больше последней принятой; устаревший запрос только продлевает сессию.
  Поэтому heartbeat, ушедший раньше свежего запроса, не может вернуть на
  сервере уже закрытый чат. Рукопожатие возвращает текущую ревизию, и reload
  продолжает нумерацию с неё, а не начинает заново. Ответ на обновление тоже
  несёт принятую ревизию: клиент, чей номер отстал (например, две вкладки
  делят одну сессию), догоняет сервер следующим запросом, не дожидаясь reload.
- Сервер раз в 10 секунд удаляет истёкшие сессии.
- `instanceId` меняется при каждом запуске `ApiServer`, поэтому сессии
  автоматически становятся недействительными после падения или остановки.
- Сессии живут только в памяти. В SQLite они не пишутся: это runtime-состояние,
  а не данные пользователя.
- Явное закрытие — `DELETE /api/v1/client/session`; если клиент не успел, TTL
  всё равно уберёт сессию.

### Web: вкладка, reload и дубликат

Правила:

- `sessionStorage` — per-tab хранилище. Reload вкладки сохраняет `sessionId` и
  `resumeSecret`, закрытие вкладки — нет.
- `localStorage` не подходит для `sessionId`: он общий для вкладок и переживает
  закрытие браузера, а нам нужны разные сессии у разных вкладок. Зато в
  `localStorage` (через `shared_preferences`) хранится `clientId`: он общий
  для вкладок одного профиля и должен переживать reload и обновление
  приложения.
- Новая вкладка не имеет `sessionId` и делает новое рукопожатие.
- Дублирование вкладки может скопировать `sessionStorage`. Поэтому перед
  рукопожатием клиент спрашивает через `BroadcastChannel`, не занят ли этот id
  другой живой вкладкой. Если занят — id и секрет стираются и выдаётся новый.
- `BroadcastChannel` не синхронизирует id между вкладками, а наоборот
  защищает от того, чтобы две вкладки стали одной сессией.

Алгоритм на старте вкладки:

1. Прочитать `sessionId` и `resumeSecret` из `sessionStorage`.
2. Если id есть — отправить в `BroadcastChannel` сообщение `claim`.
3. Если другая вкладка ответила `taken` (ожидание — до 1 секунды) — это
   дубликат: удалить id и секрет и делать рукопожатие без
   `previousSessionId`. Вкладка отвечает только за id, который действительно
   лежит в её `sessionStorage`; иначе любая открытая вкладка ломала бы reload
   соседней.
4. Если ответа нет — это reload: отправить `previousSessionId` и
   `previousSessionSecret`.
5. Записать выданные сервером id и секрет обратно в `sessionStorage`.

Обнаружение дубликата через `BroadcastChannel` — best-effort: вкладка в фоне
может не успеть ответить, и тогда сервер увидит одну сессию. Это ограничение
принято, чтобы не усложнять протокол; обычные новые вкладки и reload работают
как описано.

`sessionStorage` и `BroadcastChannel` могут быть недоступны (приватный режим,
sandbox iframe, отключённое хранилище). В этом случае клиент работает без
сохранения между reload: новый id после перезагрузки. Ошибки хранилища не
должны ломать приложение.

## Сервер

Новые маршруты:

```text
GET    /api/v1/client/probe            проверить демон и токен без сессии
POST   /api/v1/client/handshake
PUT    /api/v1/client/session          heartbeat и presence
DELETE /api/v1/client/session          закрыть текущую сессию
GET    /api/v1/client/sessions         список клиентских сессий
```

`GET /client/probe` нужен локальному GUI для discovery. Он требует Bearer, но
не требует `X-Client-Session` и не создаёт сессию: проверка не появляется в
списке клиентов и не рассылает `clientSessionsChanged`. Ответ содержит
`protocol` и `instanceId`; несовпадение `protocol` означает, что демон не
подходит.

`PUT /api/v1/client/session` принимает:

```json
{"focused": true, "activeChatId": "…", "presenceRevision": 41}
```

`focused` и `activeChatId` необязательны. Они нужны для presence: «кто открыл
чат», «на каком устройстве приложение в фокусе», «откуда запущен ход».
Отсутствующее поле не сбрасывает прежнее значение; явный `null` в
`activeChatId` очищает чат. Ответ несёт принятую `presenceRevision`.

Отдельный сигнал закрытия:

```json
{"closing": true}
```

Он планирует удаление через `closeGrace`, а не удаляет сразу. Следующий
обычный запрос или рукопожатие отменяют закрытие. Так reload не теряет
сессию, а закрытая вкладка не висит до TTL.

`GET /api/v1/client/sessions` возвращает все живые сессии экземпляра и
помечает текущую. Токен здесь не делит пользователей: он один на сервер:

```json
{
  "currentSessionId": "a1b2c3d4",
  "sessions": [
    {
      "id": "a1b2c3d4",
      "deviceId": "9f1c2d3e4a5b6c7d",
      "clientId": "8a2f…",
      "clientApp": "ProbablyWorks",
      "clientVersion": "1.2.3",
      "clientBuild": "42",
      "clientPlatform": "linux",
      "createdAt": "…",
      "lastSeenAt": "…",
      "expiresAt": "…",
      "focused": true,
      "activeChatId": "…",
      "online": true,
      "current": true
    }
  ]
}
```

`id` и `currentSessionId` — короткие fingerprint сессий, а не сырые
идентификаторы. Список нужен для присутствия и группировки, но не для
продолжения сессии; `resumeSecret` в него не попадает.

`ClientSessionRegistry`:

- `handshake(...)` создаёт сессию или переиспользует `previousSessionId`,
  только если совпали `previousSessionSecret` и `clientId` (когда он есть у
  обеих сторон);
- `touch(...)` продлевает сессию и различает `missing` и `expired`;
- `updatePresence(...)` обновляет `focused` и `activeChatId`;
- `attach`/`detach` связывают SSE-соединение с сессией, чтобы `DELETE` мог
  закрыть поток;
- `list()` отдаёт снимок для `GET /client/sessions`;
- `sweep()` удаляет истёкшие записи.

`instanceId` — поле `ApiServer`, а не настройка. Оно создаётся через
`Random.secure` при конструировании и отдаётся в `/health` и рукопожатии.
Ни в SQLite, ни в `daemon.json` его хранить не нужно: после перезапуска это
уже другой экземпляр.

Важно не путать уровни: у экземпляра один API-токен, а сессий много. Токен —
ключ к серверу, а не пользователь. Сессии не делят данные по пользователям и
не привязаны к токену. Если когда-нибудь появится многопользовательский агент,
это будет отдельная модель прав, а не следствие текущей схемы.

### Журнал доступа

В JSONL-журнал добавляются:

- `instanceId` запуска;
- `clientSession` — короткий fingerprint сессии, не сырой id;
- `deviceId` — отпечаток `X-Client-*`;
- `clientId` — короткий fingerprint стабильного id установки.

Тела, query и сам Bearer-токен по-прежнему не пишутся. Сессия не является
секретом, но и хранить её в журнале в открытом виде незачем.

### CORS

`X-Client-Session` и `X-Client-Id` добавлены в `Access-Control-Allow-Headers`.
Web-клиент отправляет их на всех API-запросах, включая SSE; поэтому
`EventSource` не используется — он не умеет задавать заголовки.

## Клиент

В `pw_client`:

```dart
abstract interface class ClientSessionStore {
  String? read(String key);
  void write(String key, String value);
  void delete(String key);
}

abstract interface class ClientSessionChannel {
  Future<bool> isActive(String id);
  void close();
}
```

Реализации по умолчанию:

- `MemoryClientSessionStore` — desktop, mobile, тесты;
- `NoopClientSessionChannel` — там, где нет вкладок.

`RemoteAgentApi`:

- делает рукопожатие один раз (single-flight) на профиль;
- хранит id и `resumeSecret` в `ClientSessionStore` по ключу профиля;
- добавляет `X-Client-Session` в REST и SSE, а `X-Client-Id` — в
  `clientHeaders` из клиентских настроек;
- при `410 session_expired` очищает id, делает рукопожатие и один раз
  повторяет запрос;
- при `401` не повторяет бесконечно, а переводит профиль в offline;
- шлёт heartbeat и останавливает таймер в `dispose`;
- отдаёт `sessionId` и `instanceId` для диагностики и UI.

`sessionKey` — id профиля: у каждого профиля своя сессия. Для локального
демона используется отдельный ключ, потому что локальный профиль создаёт
`RemoteAgentApi` напрямую, до полной загрузки `ProfileService`.

## Web: платформенный код

Используется conditional import по `dart.library.js_interop`: он работает и
для JavaScript, и для WebAssembly. `dart:html` не используется.

```dart
// lib/core/session/client_session_store.dart
export 'client_session_store_stub.dart'
    if (dart.library.js_interop) 'client_session_store_web.dart';
```

Web-хранилище:

```dart
import 'package:pw_client/pw_client.dart';
import 'package:web/web.dart' as web;

final class PlatformClientSessionStore implements ClientSessionStore {
  static const _prefix = 'pworks.session.';

  @override
```

Канал использует `BroadcastChannel` и `dart:js_interop`:

```dart
import 'dart:async';
import 'dart:js_interop';
import 'package:pw_client/pw_client.dart';
import 'package:web/web.dart' as web;

final class PlatformClientSessionChannel implements ClientSessionChannel {
  PlatformClientSessionChannel() {
    _channel = web.BroadcastChannel('pworks.client-session');
    _channel.onmessage = ((web.Event event) {
      final data = (event as web.MessageEvent).data?.dartify();
      if (data is Map) _handle(data);
    }).toJS;
  }

  late final web.BroadcastChannel _channel;
  final _messages = StreamController<Map<Object?, Object?>>.broadcast();

  @override
  Future<bool> isActive(String id) async {
    final answer = Completer<bool>();
    final sub = _messages.stream.listen((message) {
      if (message['type'] == 'taken' && message['id'] == id) {
        if (!answer.isCompleted) answer.complete(true);
      }
    });
    _channel.postMessage({'type': 'claim', 'id': id}.jsify());
    try {
      return await answer.future.timeout(const Duration(seconds: 1));
    } on TimeoutException {
      return false;
    } finally {
      await sub.cancel();
    }
  }

  void _handle(Map<Object?, Object?> message) {
    final id = message['id'];
    if (message['type'] == 'claim' && id is String) {
      _channel.postMessage({'type': 'taken', 'id': id}.jsify());
    }
    if (!_messages.isClosed) _messages.add(message);
  }

  @override
  void close() {
    _channel.close();
    unawaited(_messages.close());
  }
}
```

Stub-версии для VM повторяют интерфейс: store хранит значения в памяти,
channel всегда отвечает `false`.

`clientId` не входит в `ClientSessionStore`: это не сессия, а установка.
Его читает и создаёт `ensureClientId` через `ClientSettings`
(`shared_preferences`). На web это `localStorage` по origin, поэтому
дублированная вкладка наследует id, а другой профиль браузера получает свой;
на native — данные приложения, которые переживают обновление. Первое создание
на web сериализуется через Web Locks, чтобы две вкладки с пустым хранилищем не
записали разные id. Сброс настроек интерфейса не меняет `clientId`.

`web` добавлен в `pubspec.yaml` прямой зависимостью. После изменения
зависимостей нужен `flutter pub get`.

## Синхронизация состояния

Сессия — фундамент, но расхождения между клиентами закрывают события и
ревизии. Ниже — текущее поведение.

### 1. Карточки

`InteractionBroker` публикует `ApprovalResolved`, `QuestionResolved` и
`EditFileChangesResolved` при фактическом закрытии карточки. События уходят
по SSE как `approvalResolved`, `questionResolved`, `editFileChangesResolved`.
Второй клиент убирает карточку и пересчитывает бейдж `waiting`. `cancelChat`
(Stop) закрывает все карточки чата и порождает те же события.

Повторное закрытие уже закрытой карточки события не даёт.

### 2. Очередь

Очередь синхронизируется по двум независимым путям: чтение защищено
ревизией, а действие — устойчивым `id` элемента и той же ревизией. Одной
защиты чтения мало: без устойчивого `id` и `expectedRevision` устаревшее
окно изменило бы не тот элемент ещё до того, как придёт полный снимок.

**Чтение.** `AgentQueueChanged` передаёт полную очередь, а не только
`size`. В `GET /chats/{id}/session` и в событии есть `queueRevision`; клиент
игнорирует снимок с меньшей ревизией. Поэтому поздний HTTP-ответ не
перетирает более новое SSE-событие. Элементы очереди передаются с
устойчивым `id`, текстом, признаком события, заметкой, упоминаниями и
метаданными вложений без байтов.

**Запись.** Мутации адресуют элемент по `id`, а не по позиции, и передают
`expectedRevision` — ревизию снимка, на котором основано действие:

```text
PATCH  /chats/{id}/queue/{itemId}   {"position": 0, "expectedRevision": 3}
DELETE /chats/{id}/queue/{itemId}?expectedRevision=3
```

`PATCH` ставит элемент в начало и прерывает текущий шаг (или сразу запускает
ход, если он не идёт), `DELETE` вынимает его из очереди. Запрос без
`expectedRevision` отклоняется. Если другое окно уже изменило очередь,
сервер отвечает `409 queue_conflict` и не трогает элементы: устаревшее окно
не удалит и не повысит чужой промпт.

Почему позиция не заменяет устойчивый `id`:

- в двух окнах очередь `[A, B, C]`;
- первое окно повышает `C`, очередь становится `[C, A, B]`;
- второе окно ещё не получило событие; запрос «удалить элемент с индексом
  1» теперь попадёт в `A`, хотя пользователь выбирал `B`;
- сервер удаляет `A`, и полный снимок уже не отменяет действие.

С устойчивым `id` второе окно удалит именно `B` либо получит `409` и
перечитает очередь; чужой промпт не пострадает. С `sendNow` это важно
вдвойне: устаревшее окно не прервёт текущий шаг ради не того элемента.

**Клиент.** После конфликта он перечитывает очередь через
`GET /chats/{id}/session` и, если элемент в ней ещё есть, повторяет
действие по тому же `id` на свежей ревизии. Если элемент уже исчез, он
просто убирается с экрана, а остальные не меняются. Успешный ответ тоже
обновляет локальный снимок, поэтому следующее действие не уходит со старой
ревизией даже при задержке SSE.

`queueRevision` защищает только чтение: сам по себе он не отменяет уже
выполненное действие по устаревшему списку. Поэтому мутации несут и
устойчивый `id`, и ревизию.

### 3. Настройки и каталог

Изменяющие запросы к `/settings/*` публикуют `stateAreaChanged` с областью
`settings`, к `/models/*` и `/providers/*` — с областью `models`.
`RemoteAgentApi` сбрасывает кеш `GET /settings`, перечитывает его и только
после успешного ответа уведомляет подписчиков. Каталог и runtime
перечитываются по событию `models`.

Это покрывает модель по умолчанию, лимиты, закрепления, журнал шагов,
политику и другие настройки.

### 4. Метаданные и удаление чата

После `PUT /chats/{id}` и `PATCH /chats/{id}` сервер публикует `chatChanged`
с `chatId`. `RemoteAgentApi` превращает его в `AgentStateChanged`, и
`ChatBloc` перечитывает открытый чат, не трогая локальный черновик и
несохранённые правки.

#### Удаление чата

Раньше `DELETE /chats/{id}` публиковал только `stateAreaChanged('chats')`.
`ChatBloc` на это не подписан: он реагирует на
`AgentStateChanged`/`chatChanged`, а удаление не порождало таких событий.
Поэтому список чатов в другом окне обновлялся, а открытый чат оставался со
старыми сообщениями; при следующем перечитывании `chat == null` экран
показывал бесконечную загрузку.

Теперь удаление — отдельное событие. `DELETE /chats/{id}` и каскадная очистка
истории публикуют `chatDeleted` с `chatId` — по одному на каждый удалённый
чат, включая скрытых субагентов. `RemoteAgentApi` превращает его в
`AgentChatDeleted`, а `ChatBloc` снимает подписки, убирает черновик и
переводит экран в состояние «чат удалён». `ChatPage` по этому состоянию
заменяет маршрут стартовым экраном, только если открыт именно этот чат:
экран в фоне (например, под дублем) не закрывается. Поэтому в другом окне не
остаётся открытый чат с исчезнувшими сообщениями, а presence очищает
`activeChatId`. Если событие пропущено (например, старый сервер), то открытие
или перечитывание чата, которого уже нет, даёт то же состояние, а не
бесконечную загрузку.

`DELETE /chats/{id}` возвращает `chatIds` удалённых чатов, чтобы клиент
очистил черновики всех, включая субагентов; `ChatListCubit` использует этот
список. Старый `204` без тела поддерживается: клиент подставляет корневой
`chatId`.

### 5. Живой ход

`ChatSession` хранит текст и рассуждения текущего шага. `GET
/chats/{id}/session` отдаёт `turnSnapshot`, а при открытии/reconnect SSE
сервер сразу отправляет `turnSnapshot` для запущенных чатов. Клиент
применяет его при открытии и переподключении, поэтому догоняет уже
накопленный ответ. Снимок очищается при завершении шага и Stop.

### 6. Черновик и правки сообщений

У чата две независимые ревизии:

- `draftRevision` — черновик композера;
- `messageEditsRevision` — неотправленные правки сообщений.

Поэтому набор в поле ввода и правка пузыря больше не конфликтуют без
причины. При реальном `409 draft_conflict` клиент сохраняет оба варианта и
показывает баннер: «оставить моё» или «взять серверное». Локальный вариант не
затирается серверным молча.

Если ответ на запись потерялся, а на сервере уже лежит ровно локальная
версия, повтор считается успешной записью: клиент обновляет ревизию без
баннера. Совпадение проверяется по снимку, который ушёл в потерянной попытке,
и по сохранённым полям, а не по идентичности объектов вложений. Если
пользователь успел напечатать больше, этот текст остаётся грязным и уходит
следующим flush.

Неудачная запись не пропадает: клиент повторяет её с нарастающей паузой
(от двух секунд, не дольше тридцати). Исключение — `chat_not_found` и
`unauthorized`: чата нет или доступ отозван, повтор бессмыслен, и черновик
убирается, а не крутит запросы бесконечно.

### 7. Метаданные чата

`Chat.revision` растёт при изменении метаданных. `PATCH /chats/{id}`
принимает `expectedRevision`; при несовпадении возвращается `409
chat_conflict`. Клиент сохраняет только изменившиеся поля, перечитывает
ревизию при конфликте и повторяет точечный PATCH. Заголовок, workspace и
другие поля, изменённые другим клиентом, не затираются.

### 8. Присутствие и уведомления

`focused` и `activeChatId` уходят с heartbeat. Сервер публикует
`clientSessionsChanged`, а `GET /client/sessions` остаётся снимком.

Вместе с ними уходит `presenceRevision` — монотонный номер состояния. Клиент
сериализует отправку присутствия и назначает растущую ревизию каждому снимку;
сервер применяет запрос, только если ревизия больше уже принятой. Смена фокуса
и переход из чата в проекты не могут примениться в обратном порядке из-за
параллельного heartbeat. Запрос с устаревшей ревизией всё равно продлевает
сессию, поэтому присутствие не мешает TTL. Рукопожатие возвращает текущую
ревизию переиспользованной сессии, и reload продолжает нумерацию с неё, а не
начинает заново. Ответ на обновление присутствия тоже несёт принятую ревизию:
клиент, отставший от неё, догоняет сервер следующим запросом.

Почему присутствие нумеруется, а не просто отправляется по очереди. Очередь
упорядочивает только ещё не отправленные снимки; сеть может переставить уже
отправленные:

- окно открыло чат `A` и отправило `focused: true, activeChatId: A`;
- пользователь сразу ушёл в проекты, и ушло `activeChatId: null`;
- запросы дошли в обратном порядке — сервер снова считает чат `A` открытым.

Последствия не косметические: `PushAppNotifier.hasFocusedChat` перестаёт
отправлять push, а список экранов показывает чат, которого пользователь уже
не видит. Обратный порядок (`focused: false` позже `true`) даёт push в чат,
который открыт на экране. Поэтому номер проверяется на сервере, а не только
порядком отправки.

`activeChatId` отражает не «последний открытый чат», а то, что пользователь
действительно видит: вкладка чатов активна, а в её стеке сверху стоит
`ChatRoute`. При переходе в проекты, хосты или настройки клиент очищает
`activeChatId`, хотя стек чатов остаётся живым. Иначе другой экран считал бы
чат открытым, а push мог бы не прийти.

Клиент слушает не только корневой роутер, но и стек вкладки чатов: замена
чата внутри вкладки не всегда уведомляет корень. Без этого присутствие
обновлялось только после перезагрузки страницы, когда чат читался заново из
маршрута.

Когда рабочая область профиля закрывается (например, пользователь перешёл в
другой профиль), клиент снимает `activeChatId` и `focused`. Клиентская сессия
профиля при этом живёт: её heartbeat продолжает работать, поэтому без сброса
сервер до конца сессии считал бы чат открытым на исчезнувшем экране и не
отправлял бы по нему push.

Интерфейс показывает соседей в трёх местах:

- значок в шапке открытого чата со счётчиком других экранов, где открыт тот же
  чат; нажатие открывает тот же полный список подключённых клиентов, что и в
  панели, иначе текущий экран выглядел бы пропавшим;
- значок в строке списка чатов, если этот чат открыт ещё где-то: подсказка
  перечисляет устройства, а число показывает количество соседей. Открытый
  список экранов обновляется потоком присутствия без закрытия диалога;
- строка «Ещё N экранов» в развёрнутой боковой панели и значок в свёрнутой
  полосе: видны все подключённые экземпляры, даже если они открыли другой чат
  или вообще не открыли чат. В общем списке есть текущий экран, активный чат,
  фокус, платформа и короткий фрагмент id сессии каждого клиента. Фрагмент нужен,
  чтобы несколько вкладок одного браузера не выглядели одинаковыми строками.

Если чат открыт в активной сессии, `PushAppNotifier` не отправляет
дублирующий push.

### 8.1. Системные уведомления

Разбор модели «один агент — много окон» отметил в уведомлениях три
расхождения: серверный push подавлялся глобально, локальные уведомления
удалённых профилей не знали о presence, а закрытие карточки не убирало
уведомление из трея. Локальные уведомления и закрытие карточек исправлены:

- устойчивый id — по id карточки, чату и типу события;
- отмена и обновление по `approvalResolved`/`questionResolved`;
- проверка presence перед локальным показом;
- сверка карточек после обрыва связи и снятие уведомлений удалённого чата.

Локальные уведомления GUI для удалённых профилей идут через отдельный мост
`ProfileNoticeBridge`. У каждого уведомления есть устойчивый ключ: для карточки
— её id (`approvalId` или `questionId`), для события хода — чат и тип, для
завершения фоновой команды — id запуска. Повторный показ с тем же ключом
обновляет запись в трее, а не добавляет вторую. Поэтому два окна, получившие
одно и то же событие, обновляют одно уведомление, а не копируют его, а две
фоновые команды одного чата не стирают уведомления друг друга.

Когда карточка закрывается, `approvalResolved` или `questionResolved` отменяет
уведомление с её ключом. Это работает и для решения, принятого в этом окне, и
для решения из другого клиента. Показ ждёт проверку presence и название чата,
поэтому мост запоминает ещё не показанные карточки: если закрытие пришло
раньше показа, отменённое уведомление уже не появится. Если закрытие пришло
уже во время платформенного показа, мост убирает уведомление повторно.

Перед локальным показом проверяется presence: если чат открыт в сессии с
фокусом на другом экране или устройстве, уведомление не нужно. Проверка
запрашивает свежий `GET /client/sessions`, а не полагается на снимок, который
мог устареть после переключения устройства. Одновременные показы переиспользуют
один запрос. Своя сессия из проверки исключена: фокус этого окна уже проверяет
`PluginAppNotifier`, а отставший presence своего экрана не должен скрывать
уведомление. Если запрос не удался, уведомление показывается: пропущенный
запрос подтверждения хуже лишнего напоминания. Встроенный агент соседних
сессий не имеет и проверяет только фокус окна.

Событие закрытия карточки могло потеряться в обрыве SSE. После восстановления
связи мост перечитывает карточки тех чатов, для которых показывал уведомления,
и убирает те, которых на сервере уже нет. При удалении чата уведомления всех
его карточек снимаются сразу.

Серверный push из того же разбора по-прежнему подавляется, если чат открыт в
активной сессии: relay пока получает только общий токен и не умеет адресовать
доставку конкретному устройству. Per-device push-токены — следующий шаг модели
устройств.

### 9. Идемпотентность пользовательских действий

Отправка сообщения несёт `clientMessageId` — устойчивый идентификатор
действия. Клиент создаёт его один раз вместе с событием, а сервер хранит
вместе с сообщением. Повтор запроса с тем же id после сетевого таймаута не
создаёт второе сообщение и не запускает второй ход: сервер проверяет уже
записанное действие в этом чате.

`clientMessageId` уникален в пределах чата: одинаковый id в разных чатах
обозначает разные действия. Уникальный индекс в БД страхует от гонки, а
сессия в памяти помнит отправки, которые ещё стоят в очереди или прямо сейчас
записываются. Поэтому повтор не задваивает сообщение ни в очереди, ни в момент
записи, ни после неё.

Для черновиков и правок сообщений потерянный ответ не создаёт ложный конфликт:
если сервер уже содержит ровно ту версию, которая ушла в попытке, клиент
обновляет ревизию без баннера. Подробности сравнения и сохранения нового
текста — в разделе 6. Опасные действия с карточками и элементами очереди
защищены устойчивым id и `expectedRevision` (разделы 1 и 2).

### 10. Переподключение

После восстановления SSE или смены `instanceId` клиент не оставляет открытые
экраны со старыми данными:

- `RemoteAgentApi` перечитывает настройки, каталог и список клиентских сессий
  и сообщает `ChatListCubit`/`ChatBloc` о необходимости сверки — и при обрыве,
  и при восстановлении;
- `ChatBloc` заново открывает текущий чат, перечитывает сообщения, очередь,
  карточки и `turnSnapshot`, затем применяет актуальные `draftRevision` и
  `messageEditsRevision`;
- снимок хода отправляется даже для запущенного, но ещё пустого ответа, чтобы
  клиент не потерял состояние `isRunning`;
- `clientSessionsChanged` приходит на реальное изменение присутствия, а не на
  каждый heartbeat; подписка на реестр одна на сервер, а не на каждое SSE.

Разрывом считается любой выход из чтения потока, а не только ошибка. Если
сервер, прокси или сеть закрыли SSE по FIN без исключения, `RemoteAgentApi`
сразу переводит статус в `offline` и запускает сверку, а не остаётся в
`online` с пропущенными событиями. Успешный REST-ответ не возвращает статус в
`online`, пока поток не восстановлен: иначе UI показал бы «на связи» без
доставки событий. После повторного подключения сверка повторяется: события
между первым снимком и новым потоком тоже могли не дойти. Оболочка закрывает
открытый чат только после устойчивой недоступности, когда не отвечает и REST,
а не на короткий обрыв потока.

Поэтому пропущенные во время обрыва `messageAdded`, `approvalResolved`,
`chatChanged`, `chatDeleted` и `draftChanged` не оставляют открытый чат в
устаревшем состоянии: удалённый чат обнаруживается при перечитывании и
закрывает маршрут.

## Безопасность

- `sessionId` — идентификатор представления, а не авторизация. Bearer-токен
  остаётся обязательным на каждом запросе.
- Один экземпляр сервера — один API-токен. Он не является пользователем и не
  делит сессии: `GET /client/sessions` показывает все клиентские подключения.
  Несколько сессий — это несколько окон/устройств, а не несколько
  пользователей.
- `clientId` — стабильный ключ устройства для группировки, но не глобальный
  идентификатор и не граница безопасности. Очистка данных, переустановка или
  новый профиль браузера меняют его. `deviceId` — отпечаток описания клиента
  и запасной ключ для старых клиентов.
- Если понадобится отзыв доступа по отдельному устройству, следующим шагом
  добавляется `deviceToken`: долгоживущий секрет, выданный сервером при
  сопряжении. Это будет отдельная модель устройств, а не текущая сессия.

## Тесты

- Registry: создание, повторное рукопожатие с `previousSessionId` и
  `previousSessionSecret`, отказ без секрета и от другого `clientId`,
  истечение, `sweep`, `delete`.
- API: `/health` содержит `instanceId`; probe подтверждает токен без сессии;
  handshake возвращает сессию, `resumeSecret` и `clientId`; `requireSession`
  без заголовка — `400`; протухшая — `410`; heartbeat продлевает;
  неизменённое присутствие не рассылает лишнее событие; устаревшая
  `presenceRevision` не откатывает присутствие, но продлевает сессию;
  рукопожатие и ответ на обновление возвращают принятую ревизию; список
  сессий помечает текущую и отдаёт fingerprint вместо сырого id; `DELETE`
  закрывает; SSE принимает заголовок; CORS разрешает `x-client-session` и
  `x-client-id`.
- Client: рукопожатие ровно один раз при параллельных запросах; заголовок на
  всех запросах; `410` → рукопожатие и один retry; `401` не повторяется;
  нормальный конец SSE без ошибки переводит в `offline`, запускает сверку и
  держит статус до нового потока, после чего сверяется повторно, а сетевая
  ошибка фоновой сверки не всплывает необработанной; heartbeat; присутствие
  уходит по одному запросу с растущей ревизией; `MemoryClientSessionStore`;
  `resumeSecret` сохраняется рядом с id; `clientId` стабилен между загрузками,
  создаётся один раз при параллельных вызовах и уходит в `X-Client-Id`.
- Синхронизация: закрытие карточек, полная очередь с ревизией, инвалидация
  настроек, `chatChanged`, удаление открытого чата (включая субагентов и
  экран в фоне) и каскадной очистки истории, `turnSnapshot`, раздельные
  ревизии черновика и правок, `expectedRevision` у метаданных чата,
  обновление существующего черновика после удалённого изменения, сохранение
  при сетевой ошибке.
- Идемпотентность: повтор отправки с тем же `clientMessageId` не создаёт
  второе сообщение и не ставит его в очередь дважды; одинаковый id в разных
  чатах разрешён, а в одном чате отклоняется; сохранение черновика после
  потерянного ответа не показывает конфликт, даже если пользователь успел
  напечатать больше.
- Уведомления: устойчивый ключ карточки, события хода и фоновой команды,
  отмена по `approvalResolved`/`questionResolved`, сверка карточек после обрыва
  связи, пропуск локального уведомления, когда чат открыт в активной сессии на
  другом экране.
- Web: сценарий вкладок проверяется вручную в браузере; автоматических
  тестов `sessionStorage`/`BroadcastChannel` в репозитории нет.

## Ограничения

- Сессии не переживают перезапуск сервера; это сознательно.
- `instanceId` не стабилен между запусками; это тоже сознательно.
- `clientId` — ключ устройства для группировки, а не глобальный уникальный
  id. Очистка данных сайта или приложения, переустановка и новый профиль
  браузера создают новое устройство; `deviceId` у старых клиентов может
  совпасть у двух машин с одинаковой версией.
- Пока нет per-device токенов, отзыв доступа возможен только сменой общего
  Bearer-токена.
- Список сессий показывает клиентов, но не позволяет отозвать отдельное
  устройство: для этого нужна отдельная модель device-токенов.
- Обнаружение дубликата вкладки через `BroadcastChannel` остаётся
  best-effort.
- Пропущенные во время обрыва события догоняются перечитыванием снимков, а не
  журналом SSE с `id:`/`Last-Event-ID`: отдельного журнала событий нет.
