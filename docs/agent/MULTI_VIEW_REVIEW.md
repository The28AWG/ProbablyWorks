# Анализ модели «один агент — много окон и устройств»

Это итог разбора реализации [MULTI_VIEW.md](MULTI_VIEW.md) по духу модели, а не по
формальному списку пунктов. Главный вопрос: можно ли из любого окна или
устройства безопасно и предсказуемо работать с одним агентом, не получая
устаревшие экраны, потерянные действия и лишние уведомления.

## Итог

Основа модели правильная: разделены экземпляр сервера, клиентская сессия,
установка и устройство; есть TTL, heartbeat, presence, ревизии очереди и
черновиков, перечитывание состояния после переподключения. Это уже не «просто
несколько вкладок с общим API».

Но синхронизировано в основном **состояние**. Не до конца синхронизировано
**внимание пользователя**:

- серверный push подавляется глобально, а не по устройству: адресной доставки
  уведомлений пока нет.

Ниже — конкретные места и предложения.

## Что сделано хорошо

- `instanceId` / `sessionId` / `clientId` / `deviceId` разделены по смыслу.
  Это даёт правильную основу для «какой запуск», «какой клиент», «какая
  установка» и «какое устройство».
- `previousSessionId` и `resumeSecret` для reload, `closeGrace` и SSE-ping как
  признак жизни — продуманные детали, которые закрывают реальные сценарии
  браузера и мобильных устройств.
- Полная очередь с `queueRevision` и мутации по устойчивому id с
  `expectedRevision`, отдельные ревизии черновика и правок сообщений,
  `turnSnapshot` при переподключении — сильная часть реализации.
- Защита от устаревших ответов списка сессий и reconcile после reconnect
  показывают, что гонки уже воспринимаются как часть модели.
- Нормально завершившийся SSE считается обрывом: статус остаётся `offline` до
  нового потока, а снимки перечитываются при обрыве и после переподключения.
- Отправка сообщения идемпотентна по `clientMessageId`, а потерянный ответ на
  сохранение черновика не даёт ложного конфликта: повтор распознаётся как уже
  выполненное действие.
- В журнал доступа пишется fingerprint сессии, а не сырой id.

## Инварианты, которые стоит зафиксировать

Их полезно держать в голове при развитии модели:

1. Любое действие либо идемпотентно, либо отвергается по устаревшей ревизии.
2. Состояние на экране не переживает удаление объекта, который оно показывает.
3. Уведомление получает ровно то устройство, где пользователь действительно не
   видит событие.
4. После любого обрыва клиент догоняет состояние, а не ждёт следующего события.
5. Одна сессия — одно представление; два окна не должны незаметно слиться в
   одну сессию.

## Замечания

### 1. Трафик растёт как N × всё (низкий/средний приоритет)

> Реализовано: подписка на открытые чаты, коалесинг дельт и `stateAreaChanged`,
> снимок присутствия в `clientSessionsChanged` и полная очередь только
> подписчикам. Устройство — в [MULTI_VIEW.md](MULTI_VIEW.md), раздел 11.

Каждый клиент открывает глобальный `/events` и получает `textDelta` по всем
чатам, хотя сервер уже умеет фильтр `?chatId=`. При нескольких устройствах и
длинном ответе агента каждое окно получает весь поток токенов всех чатов.

Дополнительно:

- `clientSessionsChanged` не содержит снимка, поэтому каждое изменение presence
  вызывает по одному `GET /client/sessions` на клиент;
- `queueChanged` отправляет полную очередь с текстами и вложениями во все окна;
- `stateAreaChanged('chats')` после каждого сообщения заставляет все клиенты
  перечитывать весь список чатов.

Для текущего масштаба это терпимо, но дух «много окон» предполагает, что
добавление ещё одного экрана не должно линейно увеличивать нагрузку на все
остальные.

**Идеи:** подписка на `?chatId=` для активного чата плюс лёгкий глобальный
поток; коалесинг `textDelta`; снимок presence или `presenceRevision` в событии;
полная очередь только подписчикам этого чата.

### 2. Мелкие, но заметные детали

- На web при каждом reload с сохранённым `sessionId` выполняется `claim` и
  ожидание до 1 секунды, даже если других вкладок нет. Это заметная задержка
  первого запроса. Можно уменьшить таймаут до 100–200 мс или использовать
  Web Locks.
- Нет действия «закрыть другой экран»: сервер умеет удалять сессию по id, но
  маршрут `DELETE /client/session` закрывает только текущую. Это не отзыв
  доступа, а уборка зависших экранов.
- В `_listen()` при не-200 ответе SSE поток ответа не вычитывается и не
  закрывается. При повторяющихся `410/5xx` это потенциальная утечка соединений.

## Хорошие идеи сверх текущего

1. **Сделать устройство полноценным объектом UI.** Имя, последняя активность,
   кнопка «закрыть этот экран».
2. **Handoff между устройствами.** Нажатие на чужую сессию в списке может
   открыть тот же чат здесь.
3. **Атрибуция действий.** Показывать, с какого устройства запущен ход или
   закрыта карточка. Особенно полезно для approvals.
4. **Адресная доставка push.** Per-device токены, чтобы телефон получал
   уведомление даже тогда, когда тот же чат открыт на десктопе, вместо
   глобального подавления по активной сессии.
5. **Read-state / last-read revision.** Если появится непрочитанное, его тоже
   нужно синхронизировать между устройствами.
6. **Проверка контракта синхронизации.** Тест, который падает, если новый
   мутирующий маршрут не публикует событие или не описан в матрице общих
   ресурсов. Путь-`switch` этого не гарантирует.

## Чего не хватает в тестах

Сейчас хорошо покрыты registry, API рукопожатия, порядок присутствия,
клиентский retry, идемпотентная отправка, обрыв SSE без ошибки с повторной
сверкой после переподключения и базовые ревизии. Но именно «многооконные»
сценарии почти не проверяются:

- сквозной сценарий с двумя устройствами и одним уведомлением: подавление,
  дедупликация и отмена проверены на мосте с подставным presence, но второго
  клиента в тестах нет.
