## P0

### PW-001. Не терять историю за пределами recent window

**Статус:** готово.

**Проблема.** `ContextBuilder` отбрасывал всё, кроме последних 40 сообщений, а
`ContextCompactor` считал бюджет уже по усечённой истории. На длинном диалоге из
коротких сообщений начало терялось без сводки, хотя окно модели не было заполнено.

**Что сделано.**
- `ContextBuilder.build` отдаёт всю историю после `compactedUntilSeq`.
- `ContextCompactor` считает бюджет по полной истории.
- Триггер роста числа tool-результатов считается после границы сжатия, а не по
  последним 40 сообщениям.
- Добавлен тест: 100 сообщений при окне 40 не усекаются builder'ом.

**Критерии приёмки.**
- При истории длиннее `recentWindowMessages` модель получает либо всю историю, либо
  сводку + хвост.
- Нет случая, когда сообщения исчезают и без сводки, и без предупреждения.

**Файлы:** `lib/agent/context/context_builder.dart`,
`lib/agent/context/context_compactor.dart`.

### PW-002. Не разрывать пару tool_call / tool_result при сжатии

**Статус:** готово.

**Проблема.** Граница сжатия искалась только по user-сообщению. Если в хвосте
оказывался большой батч инструментов, сжатие либо не происходило, либо (в старом
окне) результат мог остаться без assistant-вызова.

**Что сделано.**
- `ContextCompactor._safeCutIndex` ставит границу на `user` или `assistant`.
- Если `keepFrom` попадает в `tool`/`event`, граница сдвигается назад к владельцу
  вызова.
- Добавлен тест: срез перед двумя результатами инструмента оставляет assistant и
  оба результата.

**Критерии приёмки.**
- В запросе нет `tool`-сообщения без соответствующего assistant-вызова.
- Сжатие не разрывает батч инструментов.

**Файлы:** `lib/agent/context/context_compactor.dart`,
`test/agent/context/context_compactor_test.dart`.

### PW-003. Сбрасывать устаревшую сводку после edit/delete

**Статус:** готово.

**Проблема.** `_truncate` удалял сообщения, но не трогал `compactionSummary` и
`compactedUntilSeq`. После правки раннего сообщения cutoff мог быть больше всех
оставшихся `seq`; модель получала только старую сводку.

**Что сделано.**
- Если `compactedUntilSeq > fromSeq - 1`, сводка очищается, cutoff сбрасывается в 0.
- Чат перечитывается после restore, чтобы не перезаписать новый `currentRevisionId`.
- Добавлен e2e-тест: edit после сжатия очищает сводку и cutoff.

**Критерии приёмки.**
- После edit/delete модель видит актуальную историю.
- Старая сводка не описывает удалённые сообщения.

**Файлы:** `lib/agent/loop/chat_session.dart`,
`test/agent/loop/chat_session_e2e_test.dart`.

### PW-004. Обрабатывать переполнение контекста

**Статус:** готово (частично: без жёсткого предела одного результата).

**Проблема.** `LlmFailure.contextLengthExceeded` распознавался провайдером, но не
использовался: ход падал без попытки сжатия.

**Что сделано.**
- В `_loop` ошибка переполнения вызывает `_prepare(forceCompact: true)` и один
  повтор запроса.
- Перед повтором сбрасываются текстовые дельты, чтобы не склеить два ответа.
- Вторая такая ошибка не глотается.
- Добавлен e2e-тест на повтор.

**Осталось:** жёсткий предел на один результат/вложение и fallback для батча,
который нельзя сжать без разрыва пары.

**Критерии приёмки.**
- Один раз переполнение не завершает ход ошибкой.
- Бесконечного цикла «сжать → повторить → сжать» нет.
- Слишком большой одиночный результат даёт понятную ошибку, а не молчаливый сбой.

**Файлы:** `lib/agent/loop/chat_session.dart`,
`lib/providers/ai/openrouter/openrouter_llm_provider.dart`.

## P1

### PW-008. Базовые файловые инструменты

**Статус:** готово.

**Сделано.**
- Добавлены `delete_file`, `move_path`, `copy_path`, `make_dir`, `stat_path`,
  `glob`, `apply_patch`.
- Для операций есть `HostOp`, POSIX/Windows-компиляция и реализация на
  виртуальном Host; паритет проверяется тестами.
- `glob` ищет по имени файла. Он, как и `grep`, использует обычный вывод
  журнала: отдельный вид нужен только операциям с содержимым
  (`read`/`write`/`edit`/`apply_patch`).
- `apply_patch` принимает unified diff, проверяет контекст и счётчики, применяет
  все хунки за один раз снизу вверх и пишет файл только после успешной проверки.
  Перед записью сохраняется снимок для отката; diff показывается в журнале.
  Парсер и применитель вынесены в `lib/core/util/unified_diff.dart`.
  В `packages/virtual_git` есть `GitDiffCodec` и `applyPatch`, но они завязаны
  на `GitRepository`; для local/SSH-хоста нужен независимый чистый diff.
- Удаление текстового файла попадает в changeset и восстанавливается при откате.
- `move_path` и `make_dir` помечают ход как неоткатываемый по простому правилу:
  changeset не умеет отменять переименование и создание каталога.
- Представление проверено widget-тестами: `apply_patch` открывается как diff,
  операции с путями остаются компактными строками и не создают `FileChangeView`.

**Ограничения.**
- Копирование каталогов не поддерживается.
- `apply_patch` применяется к одному файлу; несколько файлов — несколько вызовов.

**Критерии приёмки.**
- Рефакторинг не требует `run_command` для обычных файловых операций.
- Для каждого инструмента есть политика, эффект, spec и отображение в журнале.

### PW-010. stdin, timeout, persistent shell и ввод в терминал

**Статус:** готово.

**Сделано.**
- `run_command` принимает `stdin` и `timeout`; stdin идёт через pipe без PTY.
  Таймаут не может превышать лимит из Settings.
- Живой PTY принимает ввод пользователя; сохранённый вывод остаётся read-only.
  При завершении команды `CommandOutput` отключается от PTY и снова становится
  только просмотром.
- Для POSIX-команд выставляются `PAGER=cat`, `GIT_PAGER=cat`, `CI=1`, если они
  ещё не заданы. На Windows это не применяется.
- В описании инструмента явно сказано, что каждый вызов — новый shell:
  `cd`/`export` не сохраняются, нужен `cwd` или цепочка команд.
- Виртуальный Host: stdin работает через интерпретатор, PTY и ввода в терминал
  нет, background по-прежнему запрещён. Timeout и Stop теперь отменяют поток
  интерпретатора через `ActiveExec.cancel`, а не пытаются убить несуществующий
  процесс.

**Решение по persistent shell.** Не вводим: изоляция команд проще для политики,
восстановления и фоновых запусков. Вместо этого есть `cwd`, stdin, timeout и
явное правило «каждый вызов — новый shell».

**Критерии приёмки.**
- Команда, ждущая ввода, не висит 10 минут без объяснения.
- `export`/`cd`/venv описаны как несохраняемые.

### PW-011. Области подтверждений и отклонение с причиной

**Статус:** готово.

**Сделано.**
- `ApprovalDecision` заменил `bool`: отказ, один раз, для хода, для чата.
- Разрешение привязано к точной паре `toolName + summary`; широких шаблонов
  и wildcard нет. Изменившаяся команда снова спросит.
- «Для хода» живёт до конца пользовательского сообщения, «для чата» — до конца
  сессии чата; после перезапуска карточка хранит `turnId` и ключ.
- Отказ открывает `ConfirmDialog.prompt` с необязательной причиной; причина
  уходит модели в результате инструмента.
- При нескольких карточках появляется `AppBanner` с «Разрешить все один раз».
- В карточке подтверждения четыре действия: «Отклонить», «Этот ход»,
  «Этот чат», «Подтвердить». Используются существующие `ActionCard`, `AppBanner`
  и `ConfirmDialog`; golden обновлён.

**Решение по шаблонам.** «Запомнить шаблон» не вводим: точное разрешение
безопаснее и предсказуемее. Пользователь может разрешить конкретное действие
на ход или чат.

**Критерии приёмки.**
- Ask-режим не требует десятки одинаковых подтверждений.
- Модель понимает, почему действие отклонено.

### PW-012. Regenerate и форк текущего чата

**Статус:** готово.

**Решение.** Явного отката изменений в интерфейсе нет и не будет. Откат
существует только как часть процесса: edit/delete сообщения и regenerate.
Ветка от произвольного старого сообщения несовместима с общим Host: файлы
сейчас в текущем состоянии, а не в состоянии того сообщения. Поэтому вместо
неё — форк текущего чата.

**Сделано.**
- `ChatSession.regenerateLast` находит последнее пользовательское сообщение,
  вызывает тот же `_confirmFileChangesBeforeRewind`, что и edit, удаляет только
  ответы после сообщения и запускает ход заново. Сообщение пользователя
  не дублируется.
- Кнопка regenerate — у последнего ответа, рядом с копированием.
- `AgentHub.forkChat` копирует историю, вложения, завершённые tool runs и
  состояние в новый чат. С `untilMessageId` копируются только ходы до
  указанного ответа включительно, а состояние берётся из ревизии последнего
  пользовательского сообщения этого отрезка.
- У каждого завершённого ответа есть действия в порядке: копировать,
  regenerate (только последний ответ), форк от этого ответа.
- В меню чата остался пункт «Дублировать» для копии всего чата.
- Файлы не копируются и не откатываются; исходный чат и его состояние
  не меняются.

**Критерии приёмки.**
- Regenerate не требует отдельного отката: используется тот же неявный диалог.
- Форк не ломает исходную историю и файлы.
- В интерфейсе нет самостоятельной кнопки отката.

### PW-013. Context inspector, стоимость и бюджет

**Статус:** готово.

**Проблема.** В диалоге контекста было видно только число токенов и кнопка
сжатия. Пользователь не понимал, что занимает окно, сколько стоит запрос и
почему история внезапно сжалась. Дневной лимит трат отсутствовал.

**Что сделано.**
- `ContextBreakdown` считает символы по system-промпту, диалогу, результатам
  инструментов, вложениям и схемам инструментов; в диалоге показывается
  примерная оценка токенов.
- Стоимость последнего запроса считается по ценам модели из каталога, расход
  дня накапливается в kv-настройках по чату и дате.
- Дневной лимит задаётся на чат через диалог контекста; пустое значение снимает
  лимит. Перед шагом модели превышение лимита останавливает ход с сообщением,
  где указаны текущий расход и лимит.
- `ChatCompactionInfo` хранит время, причину, границу и длину сводки последнего
  сжатия; диалог показывает «когда и почему».
- Битая запись расхода или метаданных сжатия не ломает чат: она читается как
  отсутствующая.
- При удалении чата его дневной лимит, накопленный расход и метаданные сжатия
  удаляются из kv-настроек, чтобы ключи не копились.

**Критерии приёмки.**
- Пользователь видит, что занимает окно и сколько стоит ход.
- Превышение бюджета останавливает ход с понятным сообщением.
- В диалоге видно время и причину последнего сжатия истории.

**Файлы:** `lib/agent/context/context_breakdown.dart`,
`lib/agent/loop/agent_event.dart`, `lib/agent/loop/chat_session.dart`,
`lib/core/data/settings_repository.dart`, `lib/core/domain/chat_usage.dart`,
`lib/features/chat/presentation/bloc/chat_bloc.dart`,
`lib/features/chat/presentation/widgets/chat_context_dialog.dart`,
`lib/features/chat/presentation/widgets/chat_view.dart`.

  `mcp_dart`, stdio и Streamable HTTP, импорт/экспорт `mcp.json`, ленивое
  подключение и вкладка настроек.
- Плагины — отдельные скомпилированные пакеты с флагом включения, своими ARB и
  делегатом локализации. Зависимости разрешаются графом: при включении
  предлагается включить недостающие, при отключении показываются зависимые.
- Первый плагин — декларативные команды: фиксированные executable и args,
  запуск без shell-интерполяции, таймаут и собственный экран настроек.
- Второй плагин — декларативные HTTP-инструменты: метод, URL, заголовки, тело,
  JSON-схема аргументов и подстановки `{{arg}}`. Ответ можно оставить текстом,
  разобрать через JSONPath или извлечь текст из HTML по CSS-селектору.
- Для remote MCP добавлен OAuth authorization-code с PKCE и локальным
  loopback-callback; токены хранятся в `SecretStore`.

**Критерии приёмки.**
- Новый инструмент подключается без правки `ToolExecutor`.
- Внешний инструмент не может обойти policy.

### PW-015. Субагенты

**Статус:** готово.

**Что сделано.**
- `delegate_task` принимает `title`, полный self-contained `task` и
  необязательный `context`; запускает скрытый чат и сразу возвращает `runId`.
- `wait_subagent` ждёт завершения и возвращает только статус и размер отчёта.
- `read_subagent_report` читает отчёт страницами по `offset`/`limit`, поэтому
  длинный отчёт не обязан целиком влезать в контекст родителя.
- Без ожидания результат приходит в root-чат коротким событием.
- В контексте родителя появляется список активных субагентов.
- Модель субагента: настройка или модель родителя; `parent`/`default` в
  инструменте, произвольный id выбрать нельзя.
- Подтверждения субагента показываются в root-чате, стоимость агрегируется
  туда же.
- Карточка `delegate_task` открывает скрытый чат в read-only режиме без
  композера и редактирования.
- Удаление родителя рекурсивно удаляет субагентов; Stop останавливает детей.
- Активные и недоставленные субагенты восстанавливаются после перезапуска.
- При завершении хода с активными субагентами добавляется мягкое напоминание.
- Повторно открытые подтверждения субагента регистрируются в root-чате.
- Карточка `delegate_task` и отсутствие композера в скрытом чате покрыты
  виджет-тестами.

**Файлы:** `lib/agent/subagent/`, `lib/agent/loop/chat_session.dart`,
`lib/agent/loop/agent_hub.dart`, `lib/agent/tools/tool_executor.dart`,
`lib/core/data/chat_repository.dart`, `lib/core/db/tables.dart`,
`lib/features/chat/presentation/widgets/chat_view.dart`,
`lib/features/chat/presentation/widgets/chat_step_ledger.dart`,
`lib/features/settings/presentation/bloc/settings_cubit.dart`.

**Критерии приёмки.**
- Исследование и реализация могут идти параллельно.
- Субагент не теряет доверие workspace и policy родителя.

### PW-017. Headless/daemon/remote API и планировщик

**Статус:** частично.

**Что сделано.**
- Ядро вынесено в чистый Dart-пакет `pw_agent`; HTTP API и headless-запуск —
  в `pw_server`. Клиент не импортирует `pw_server`; старые `pw_api` и
  `pw_daemon` удалены.
- Демон работает без Flutter, владеет базой и запускает recovery, MCP,
  каталог моделей, плагины и планировщик.
- Ядро плагинов вынесено в чистые Dart-пакеты и работает в демоне; HTTP API
  управляет списком, зависимостями, флагами и настройками плагинов.
- HTTP API покрывает не только чаты и карточки, но и хосты, проекты, факты,
  skills, политики, настройки агента, ключ OpenRouter, модели, MCP, плагины,
  аудит окружения, вложения, usage, очередь, действия сессии и расписания.
- Удалённый клиент работает через профильные маршруты `/a/<profileId>/...`,
  показывает те же вкладки, настройки и карточки, передаёт вложения и
  получает уведомления. Списки чатов, хостов и проектов обновляются по SSE
  `stateAreaChanged`, без периодического polling-а.
- Добавлены настройки push-уведомлений профиля и серверный relay-транспорт:
  без URL и токена push не отправляется.
- Клиентские настройки (язык, тема, ширина панели и реестр профилей)
  вынесены в `shared_preferences`; для них GUI больше не читает БД агента.
- Черновики и неотправленные правки хранятся в backend'е чата, синхронизируются
  через API/SSE и имеют `draftRevision` для разрешения конфликтов.
- API локального профиля собраны в `LocalAgentApis`; `ProfileService` больше не
  зависит от конкретных локальных адаптеров. Это позволяет подменить bundle
  на `RemoteAgentApi` локального демона без изменения UI.
- GUI находит локальный демон через `daemon.json`, проверяет protocol/health/токен
  и подключает локальный профиль через loopback API. Без демона остаётся
  embedded-режим.
- На desktop GUI автоматически запускает локальный демон, если его нет: в dev —
  через `dart run`, в сборке — готовый бинарник рядом с GUI. Перед запуском
  проверяется блокировка БД, чтобы не поднять второй процесс на той же базе.
- Настроена упаковка через Fastforge: AppImage, DEB, tar.gz/zip для Linux,
  Windows EXE и macOS DMG. В пакет попадает AOT-демон с нативными
  библиотеками (`daemon/bin` и `daemon/lib`).
- Добавлены GitHub Actions: CI с format/analyze/тестами и release-workflow,
  который по тегу `v<version>` собирает GUI для Linux x64, Windows x64,
  macOS arm64/x64, Snap amd64 и отдельные standalone-архивы сервера,
  публикует GitHub Release и SHA256SUMS.
- Snap собирается отдельно через `snapcraft` в classic-режиме и публикуется в
  канал `edge`; GTK3 и зависимости входят в stage-packages.
- Добавлен интеграционный тест реального демона: процесс стартует, пишет
  `daemon.json` с правами `0600`, отвечает на `/health` и `/settings`,
  корректно завершается по SIGTERM и удаляет discovery-файл.
- Демон использует OS-keyring там, где он доступен: Secret Service на Linux
  и Keychain на macOS. Токен API и секреты мигрируют из `secrets.json`;
  если keyring недоступен, остаётся файловый fallback `0600`.
- Ведётся отдельный JSONL-журнал доступа к API с метаданными запросов,
  fingerprint токена, ротацией и CLI-анализом (`summary`, `problems`,
  `filter`).
- Bearer-токен в `SecretStore`, loopback по умолчанию, лимит тела запроса,
  таймауты и явный `--bind` для удалённого доступа.
- Планировщик отложенных задач в SQLite (`scheduled_tasks`), переживает
  перезапуск.
- Контракт API и ограничения описаны в [DAEMON.md](DAEMON.md), модель угроз —
  в [SECURITY.md](SECURITY.md).

**Осталось.**
- Snap-пакет ещё не собран и не установлен на реальной системе: локальная
  сборка блокируется Ubuntu Pro, проверка будет в CI. Classic-режим требует
  ручной проверки Snap Store.
- Windows EXE и macOS DMG собираются в CI, но установка и запуск ещё не
  проверены на реальных ОС; для публичного релиза нужна подпись Authenticode
  и notarization macOS.
- Windows Credential Manager для демона подключён через FFI, но ещё не
  проверен на реальной Windows-машине. Нужна проверка и подпись установщика.
- Встроенного TLS нет; в [DAEMON.md](DAEMON.md) добавлена инструкция с
  SSH-туннелем, Caddy и nginx (SSE, таймауты, токен).
- Нет интеграционного теста планировщика с реальным агентом: проверены HTTP
  API на фейковом backend, клиент с реальным `ApiServer` и запуск настоящего
  демона без выполнения хода.

**Критерии приёмки.**
- Задача может продолжиться при закрытом окне. — выполнено для демона.
- Удалённый клиент видит те же карточки, журнал, вкладки и настройки. —
  выполнено через профильный HTTP API и SSE.
- Удалённый клиент не может обойти серверные ограничения политики и
  плагинов. — проверка плагинов выполняется в `LocalPluginApi`, ответ
  `409 agent_busy`.

**Безопасность:** модель угроз, MVP-минимум и меры изоляции агента описаны в
[SECURITY.md](SECURITY.md), запуск и ограничения — в [DAEMON.md](DAEMON.md).
