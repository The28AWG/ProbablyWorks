### PW-022. Полное маскирование секретов в `Redactor`

**Статус:** todo. Найдено при аудите вне текущего списка.

**Проблема.** `Redactor` маскирует только OpenRouter-ключи, `Bearer`,
приватные ключи и значения вида `api_key=`/`token=`. Фактическая проверка
показывает пробелы:

- `Authorization: Basic <base64>` превращается в
  `Authorization: *** <base64>`: маскируется только схема, а учётные данные
  остаются;
- `PROBABLY_WORKS_LLAMACPP_KEY=...` и другие имена провайдеров с суффиксом
  `_KEY` не маскируются, потому что шаблон ищет `api_key`, а не произвольный
  `_KEY`;
- токен Hugging Face (`hf_...`) в свободном тексте не маскируется, только
  внутри `HF_TOKEN=...`.

`Redactor` применяется к логам, выводу инструментов, истории, памяти и
ошибкам, поэтому такие значения могут попасть в БД, контекст модели и журнал.
Это противоречит обещаниям в `README.md` и `SECURITY.md`.

**Что сделать.**
- Добавить схемы `Basic`, `Digest`, `Token` и имена вида `*_KEY`, а также
  формат `hf_...`.
- Дополнительно регистрировать фактические значения из `SecretStore` на время
  жизни процесса и вырезать точные совпадения. Регулярные выражения оставить
  страховкой для значений, которых нет в хранилище.
- Покрыть тестами все форматы и отрицательный случай: обычный текст не
  меняется.

**Критерии приёмки.**
- `Authorization: Basic ...`, `*_KEY=...` и `hf_...` в свободном тексте не
  содержат исходного секрета после redaction.
- Логи, вывод инструментов, память и ответы об ошибках используют один и тот
  же механизм маскирования.
- Тест с реальным значением из `MemorySecretStore` подтверждает маскирование
  без знания формата секрета.

**Файлы:** `packages/pw_agent/lib/core/util/redactor.dart`,
`packages/pw_agent/lib/core/security/secret_store.dart`,
`test/core/core_utils_test.dart`,
`test/agent/context/untrusted_redaction_test.dart`.

### PW-024. Лимиты, таймауты и безопасные ошибки HTTP API

**Статус:** todo. Найдено при аудите вне текущего списка.

**Проблема.** У `ApiServer` есть только лимит тела запроса и heartbeat для SSE.
Нет таймаута на обработку запроса, ограничения одновременных запросов и
rate limit. Ошибка 500 отдаётся клиенту как `'$error'` без `Redactor`, поэтому
в ответ могут попасть пути, команды и внутренние детали. `SECURITY.md` требует
все эти ограничения, а демон можно явно привязать к внешнему интерфейсу.

**Что сделать.**
- Добавить token bucket по IP или fingerprint токена и ограничение числа
  одновременных запросов.
- Ввести общий таймаут обработки запроса; для SSE — отдельное поведение.
- Отдавать наружу обезличенный `internal_error`, а детали писать в лог через
  `Redactor`.

**Критерии приёмки.**
- Превышение лимита возвращает `429`, число параллельных запросов ограничено.
- Зависший backend не удерживает HTTP-соединение бесконечно.
- Ответ 500 не содержит путей, команд, имён файлов и секретов.

**Файлы:** `packages/pw_server/lib/src/api/api_server.dart`,
`packages/pw_server/lib/src/api/api_access_log.dart`,
`docs/agent/SECURITY.md`.

### PW-025. Устойчивый keyring без постоянного отката в файл

**Статус:** todo. Найдено при аудите вне текущего списка.

**Проблема.** `SystemSecretStore` при любой ошибке чтения, записи или удаления
выставляет `_usingKeyring = false` до конца жизни процесса. После этого
секреты пишутся в `secrets.json` с правами `0600`. Разовый сбой D-Bus,
Keychain или Credential Manager либо таймаут 5 секунд приводит к постоянному
downgrade; пользователь видит только запись в логе.

**Что сделать.**
- Повторять операцию с keyring ограниченное число раз и пробовать снова при
  следующей записи, а не отключать его навсегда.
- Показывать фактический backend в аудите и предупреждать пользователя о
  переходе на файл.
- Покрыть сценарии: временный сбой, постоянный сбой, восстановление keyring.

**Критерии приёмки.**
- Временный сбой не переводит процесс в файловый режим до перезапуска.
- Пользователь видит, где хранится секрет, и может повторить попытку keyring.
- Тест подтверждает возврат к keyring после восстановления backend.

**Файлы:** `packages/pw_agent/lib/core/security/system_secret_store.dart`,
`packages/pw_agent/lib/core/security/file_secret_store.dart`,
`packages/pw_agent/lib/core/security/security_audit.dart`,
`lib/core/security/secret_store_plugin.dart`.

### PW-026. Полнота проверок CI и release

**Статус:** todo. Найдено при аудите вне текущего списка.

**Проблема.** CI запускает тесты только для `pw_agent`, `pw_client`,

- Добавить `flutter build web -t lib/main_web.dart` в CI.
- В release выполнять analyze, format и тесты пакетов или переиспользовать
  проверенный job из CI.
- Добавить pre-push hook или явную локальную проверку DCM, не меняя правило
  AGENTS.

**Критерии приёмки.**
- Новый пакет с тестами не остаётся вне CI незамеченным.
- Поломка web-сборки ловится до merge.
- Тег не позволяет выпустить код, не прошедший analyze и тесты пакетов.

**Файлы:** `.github/workflows/ci.yml`,
`.github/workflows/release.yml`, `docs/agent/PACKAGING.md`.

### PW-029. Надёжность SSE и файлового хранилища секретов

**Статус:** todo. Найдено при аудите вне текущего списка.

**Проблема.** `FileSecretStore.write` делает read-modify-write без блокировки:
две одновременные записи могут потерять одну. `RemoteAgentApi` переподключает
SSE с фиксированной паузой 3 секунды без backoff и jitter, а при `401`
продолжает переподключаться бесконечно.

**Что сделать.**
- Сериализовать записи `FileSecretStore` или использовать атомарную замену с
  блокировкой.
- Добавить exponential backoff с jitter для SSE.
- Останавливать переподключение при `401` и показывать ошибку авторизации.
- Покрыть гонку записи и поведение reconnect тестами.

**Критерии приёмки.**
- Параллельные записи разных секретов не теряют значения.
- После серии ошибок интервал reconnect растёт, а не остаётся постоянным.
- Неверный токен не приводит к бесконечному циклу запросов.

**Файлы:** `packages/pw_agent/lib/core/security/file_secret_store.dart`,
`packages/pw_client/lib/src/remote_agent_api.dart`,
`packages/pw_agent/test/core/`, `packages/pw_client/test/`.
