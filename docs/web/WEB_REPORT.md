# Web-версия ProbablyWorks: теоретический отчёт

Статус: **отчёт, без реализации**. Код web-сборки, мостов и серверов в проекте не написан и не планируется в текущем этапе. Документ фиксирует, что уже известно о web, чтобы в будущем не начинать с нуля.

Дата проверки: 3 ноября 2026. Версии зависимостей берутся из `pubspec.lock` проекта (см. раздел «Источники»).

## 1. Зачем это нужно и что уже решено

ProbablyWorks — desktop- и мобильный агент. Он выполняет команды на хосте: локальном (PTY) или удалённом (SSH). Браузер не даёт ни того, ни другого «из коробки»:

- нет TCP-сокетов, поэтому SSH напрямую не работает;
- нет процессов и PTY;
- нет доступа к файловой системе пользователя.

Поэтому web — это не «перекомпилировать и открыть», а отдельная архитектура с сервером между браузером и хостом. Пока этот выбор не сделан, web не поддерживается.

## 2. Что в текущем коде мешает web (проверено по исходникам)

| Область | Где в коде | Почему не работает в браузере |
|---|---|---|
| Процессы и файлы | 12 файлов с `dart:io`: `lib/host/local_host_runtime.dart`, `lib/host/portable_pty_launcher.dart`, `lib/host/ssh_connection_pool.dart`, `lib/agent/exec/exec_log_store.dart`, `lib/core/db/db_connection.dart`, `lib/core/logging/app_log.dart`, `lib/core/data/host_repository.dart`, `lib/providers/ai/openrouter/openrouter_llm_provider.dart` и др. | `dart:io` в браузере отсутствует. ## 3. Варианты архитектуры

Ниже варианты с тем, что обязательно реализовать, что ломается и какой объём работ. Оценка объёма относительная (S, M, L, XL).

### A. SSH через WebSocket-мост

Браузер открывает `wss://` к мосту, мост открывает TCP к SSH-серверу. `dartssh2` поддерживает кастомный `SSHSocket`. Пример лежит в пакете: `tool/ws_bridge.dart` (WebSocket → TCP), используется в тестах web-сборки `dartssh2`.

- Обязательно: мост с аутентификацией, allow-list целей, лимитами, проверкой `Origin`; проверка ключа хоста в самом приложении (браузер не должен доверять мосту молча); хранилище `known_hosts` в браузере или на сервере.
- Ломается: локальный Host (PTY) не работает вообще; `dart:io` в исходниках; база и файлы на web; `path_provider`.
- Что проверено: `dartssh2` 4.1.0 содержит `tool/ws_bridge.dart` с комментарием, что браузер не открывает TCP и мост нужен.
- Объём: L. Главный риск: мост становится открытым прокси, если его не ограничить.

### B. Удалённый PTY-сервер через `portable_pty`

`portable_pty` в версии 0.0.7-beta.2 описывает web-транспорт: на web он работает поверх WebSocket или WebTransport и подключается к PTY-серверу. Shell запускает сервер на целевой машине. По сути, это удалённый Local Host.

- Обязательно: сам PTY-сервер (его нужно писать и поддерживать на каждой целевой машине), аутентификация, TLS, защита от cross-site WebSocket hijacking.
- Ломается: агенту нужен PTY на сервере, а не на устройстве пользователя; SSH-хосты остаются отдельным путём.
- Что проверено: в README пакета перечислены платформы, web указан как «WebSocket / WebTransport, pure Dart».
- Объём: XL. Фактически это свой сервис удалённого выполнения.

### C. Linux в браузере через WASM-эмулятор

Например, WebVM (CheerpX) или v86. Внутри браузера работает изолированная Linux-машина. Агент выполняет команды в ней, файлы пользователя не трогаются.

- Обязательно: проверить лицензию движка (условия использования отличаются), производительность на слабых устройствах, сетевые ограничения (внутри VM нет доступа к хостам пользователя без моста), размер загрузки.
- Ломается: это не доступ к машине пользователя. Агент работает в песочнице. Для задач «почини мой сервер» вариант не подходит.
- Объём: L–XL, зависит от движка. Не проверено в этом проекте.

### D. VNC или noVNC (удалённый рабочий стол)

Агент получает картинку рабочего стола, а не текст.

- Обязательно: VNC-сервер на целевой машине, мост WebSocket → VNC, извлечение текста через OCR или accessibility-дерево.
- Ломается: агент работает с картинкой. Текст вывода команд не структурирован, его трудно разбирать и хранить.
- Объём: XL. Для текущей модели агента (инструменты с текстовым выводом) неудобно.

### E. Web без выполнения команд

Только просмотр истории чатов, выполнение на desktop или мобильном устройстве, управление ими через web-интерфейс.

- Обязательно: синхронизация или связь с работающим приложением (тоже сервер, но без shell).
- Ломается: сам агент на web не работает, только просмотр и управление.
- Объём: M.

## 4. Сравнение

| Критерий | A. SSH-мост | B. Удалённый PTY | C. WASM-Linux | D. VNC | E. Только просмотр |
|---|---|---|---|---|---|
| Работает с серверами пользователя | да (по SSH) | да (нужен PTY-сервер) | нет (песочница) | да (картинка) | нет |
| Текстовый вывод для агента | да | да | да | нет (OCR) | — |
| Нужен свой серверный код | мост | PTY-сервер | нет (но нужен хостинг) | мост | сервер синхронизации |
| Локальный Host (PTY) на web | нет | через сервер | внутри VM | нет | нет |
| Риск безопасности | средний (открытый прокси) | высокий (удалённый shell) | низкий (изоляция) | высокий (полный рабочий стол) | низкий |
| Объём | L | XL | L–XL | XL | M |

Предварительный вывод без реализации: для агента, который работает с серверами пользователя по SSH, самый реалистичный путь — вариант A. Вариант B нужен, если понадобится локальный Host в браузере с управлением удалённой машиной. Вариант C подходит для песочницы, но не для работы с реальными хостами.

## 5. Требования безопасности (обязательны для любого web-варианта)

- Только `wss://` (TLS сам по себе не защищает от подмены, нужна проверка сертификата и `Origin`).
- Токен доступа не передаётся в query string (попадает в логи и историю).
- Проверка `Origin` на сервере (защита от cross-site WebSocket hijacking).
- Allow-list целей `host:port` на мосту, никакого открытого прокси.
- Лимиты: размер кадров, число соединений, таймауты.
- Проверка ключа хоста SSH в самом приложении, а не только в браузере.
- Пароли и приватные ключи в браузере по умолчанию не сохраняются. Если нужны, то с `wrapKey` и предупреждением пользователю.
- CSP с ограничением `connect-src` до разрешённых мостов и OpenRouter.
- Терминал только для вывода, как и на остальных платформах: ввод с клавиатуры в PTY не передаётся.

## 6. Что уже известно о производительности и ограничениях браузера

- Фоновые вкладки: браузер троттлит таймеры и может закрыть WebSocket. Долгие команды в фоне потребуют переподключения и восстановления состояния.
- Память: загрузка `sqlite3.wasm` и Flutter web увеличивает объём первой загрузки; на слабых устройствах это заметно.
- Файлы: доступ через File System Access API (только Chromium) или через `input type=file` (только выбор, без записи в папку).

Эти пункты не измерялись в проекте, они основаны на поведении браузеров и документации.

## 7. Что уже сделано для мобильной и desktop версий и почему это важно для web

- Отказ от `flutter_pty` в пользу `portable_pty`: `portable_pty` ориентирован на кросс-платформенный PTY и удалённый транспорт, поэтому, если web понадобится, точка замены уже есть (`lib/host/portable_pty_launcher.dart`).
- Вложения передаются модели содержимым, а не путём. Это не зависит от платформы и остаётся таким же для web.
- Терминал только отображает вывод.
- Мобильный SSH: Android держит соединение foreground-сервисом, пока работает агент. iOS не держит соединение в фоне.

## 8. Открытые вопросы для следующего этапа

1. CORS OpenRouter из браузера: нужна проверка запросом с другого origin, пока не проверено.
2. Лицензия и условия использования WASM-Linux (вариант C).
3. Поведение `desktop_drop` на web и альтернатива для drag-and-drop.
4. Нужно ли хранить `known_hosts` на сервере (мост) или в браузере.
5. Кто будет поддерживать PTY-сервер и мост: пользователь или сервис.
6. Требования к производительности на телефонах в браузере (Safari на iOS имеет ограничения на WebSocket в фоне).
