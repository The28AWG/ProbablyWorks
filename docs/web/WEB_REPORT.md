# Web-версия ProbablyWorks: теоретический отчёт

Статус: **отчёт, без web-сборки**. Каталог `web/` содержит шаблон Flutter (`index.html`, `manifest.json`), продуктового web-кода нет. Виртуальный Host, добавленный после предыдущей редакции, меняет архитектуру песочницы, но не делает текущее приложение собираемым в браузере.

Дата проверки: 5 ноября 2026. Версии зависимостей — из `pubspec.lock` (раздел «Источники»).

## 1. Что изменилось

Предыдущая редакция (3 ноября) исходила из двух способов выполнить команду: локальный PTY и SSH. Оба в браузере недоступны, поэтому web выглядел как отдельный сервер между браузером и машиной пользователя.

Сейчас есть третий Host. `VirtualHostRuntime` выполняет и операции, и команды внутри процесса приложения:

- в пакете `packages/virtual_host` нет `dart:io`, `dart:ffi` и `dart:isolate`;
- процессов и PTY нет (`hasTerminal` = false), фоновый запуск инструмент отвергает;
- оболочка — подмножество bash в чистом Dart (`docs/shell.md`);
- файлы — виртуальная ФС (`docs/virtual-fs.md`): постоянный слой в базе, `/tmp` в памяти процесса, снимок ОС в памяти и только для чтения;
- инструменты агента и чтение workspace идут через `HostOp` / `HostRuntime`, а не через оболочку ОС. `WorkspaceContextLoader` прямо рассчитан и на виртуальный Host.

Для сценария «агент работает в песочнице, не трогая машину пользователя» отдельная Linux-VM в WASM больше не нужна: эта песочница уже написана и используется на desktop. Доступ к реальному компьютеру по-прежнему требует процесса на этой машине. Само приложение в браузере по-прежнему не компилируется.

Отдельно зафиксирована идея удалённого Host (вариант G). Это четвёртая сущность, не продолжение виртуального Host. На машине с файлами запускается сервер, в консоль печатаются адрес и секрет, в приложении они вводятся как данные хоста. Исполнение на сервере — уже написанный локальный рантайм, трафик — WebSocket. В коде сервера и такого вида хоста нет.

## 2. Что виртуальный Host даёт web и чего не даёт

Даёт:

- выполнение команд и файловые инструменты без PTY, TCP и чужого сервера;
- ту же политику (Ask / yolo, запрет эскалации и критических команд через `command_shield`) и тот же цикл агента;
- границу «агент видит только VFS»: снимок только для чтения, чужие uid не выдаются, скрипты `/bin/sh` не исполняются.

Не даёт:

- сборку текущего дерева в web: фабрика рантаймов, старт и журнал по-прежнему импортируют `dart:io`;
- базу, секреты, логи и вложения в браузере — они завязаны на файлы ОС;
- машину пользователя и его SSH-серверы; для своей машины зафиксирована идея удалённого Host (вариант G), в коде её нет;
- полный bash и произвольные бинарники. Состав языка и расхождения — в `docs/shell.md`;
- SSH для git. На web транспорт `packages/virtual_git` — только `package:http`.

Постоянные файлы виртуального Host лежат в той же SQLite, что и чаты (`VirtualFsRepository`). Реализация `VfsStore` в памяти есть (`InMemoryVfsStore`) и сама по себе браузеру подходит; в приложении она держит только `/tmp`. Снимок (`OsSnapshot`) в базу не пишется.

## 3. Что в текущем коде мешает web

Компиляция падает на первом импорте `dart:io`. Эти файлы входят в граф от `bootstrap` и DI, поэтому обойти их выбором только виртуального Host нельзя.

| Область | Где в коде | Почему не работает в браузере |
|---|---|---|
| Старт и каталоги | `lib/app/bootstrap/app_paths.dart`, `lib/app/bootstrap/bootstrap.dart` | `path_provider` 2.1.6 на web не отдаёт каталог приложения. Блокировка второго экземпляра — файл `instance.lock`. |
| База | `lib/core/db/db_connection.dart` | `NativeDatabase` (`drift` 2.35.3, `sqlite3` 3.8.0, `dart:ffi`). На web нужны `sqlite3.wasm` и drift worker. В этой базе лежат и чаты, и постоянный слой VFS. |
| Журнал | `lib/core/logging/app_log.dart` | Ротация файлов через `dart:io`. |
| Логи команд | `lib/agent/exec/exec_log_store.dart` | Буфер вывода на время запуска — файл, в том числе для виртуального Host. После завершения текст переносится в SQLite. |
| Хосты | `lib/core/data/host_repository.dart` | `Platform.isMacOS` / `Platform.isWindows` при создании локального Host. |
| Сборка рантайма | `lib/host/host_runtime_factory.dart`, `lib/app/di/injection.config.dart` | Одна фабрика импортирует локальный, SSH и виртуальный рантаймы. DI всегда создаёт `PortablePtyLauncher` и `SshConnectionPool`. |
| Локальный Host | `lib/host/local_host_runtime.dart`, `lib/host/portable_pty_launcher.dart`, `portable_pty` 0.0.7-beta.2 | `Process` и нативный PTY. На web пакет умеет только клиент к удалённому PTY-серверу. |
| SSH | `lib/host/ssh_connection_pool.dart`, `lib/host/host_diagnostics.dart`, `dartssh2` 4.1.0 | TCP-сокет. Пакет предлагает свой `SSHSocket` поверх WebSocket. |
| Пути ключей | `lib/core/util/home_path.dart` | `Platform.environment` для `~`. |
| Вложения | `lib/agent/attachments/attachment_loader.dart` | Читает `File` с диска. На web выбор файла даёт байты, а не путь ОС. |
| OpenRouter | `lib/providers/ai/openrouter/openrouter_llm_provider.dart` | Библиотека `openrouter` в `lib/` `dart:io` не импортирует. Адаптер импортирует его ради `SocketException`. CORS с другого origin не проверен. |
| Платформа в UI | `lib/core/platform/app_platform.dart` | Решений про web нет, `kIsWeb` нигде не используется. `defaultTargetPlatform` в браузере — ОС устройства, поэтому desktop-браузер получил бы локальный Host и PTY, телефонный — ветку «мобильный». |
| Секреты | `flutter_secure_storage` 11.2.0 | На web значения в `localStorage`, ключ AES-GCM по умолчанию тоже там. |
| Файлы в UI | `file_selector` 1.1.x, `desktop_drop` 0.8.4, импорты в `chat_view.dart` и диалоге хоста | `file_selector` web поддерживает. `desktop_drop` для браузера не проверен, импорт безусловный. |
| Уведомления | `flutter_local_notifications` 22.3.1 | Есть web-пакет. Нужны разрешение браузера и проверка фоновой вкладки. |

Виртуальный рантайм в этот список не входит: он уже исполняется без ОС. Мешает не он, а то, что приложение не умеет стартовать без файлов и тащит локальный и SSH-рантаймы в ту же сборку.

## 4. Варианты архитектуры

Оценки объёма относительные (S, M, L, XL) и относятся к оставшейся работе, не к уже написанному виртуальному Host.

### A. SSH через WebSocket-мост

Браузер открывает `wss://` к мосту, мост открывает TCP к SSH-серверу. `dartssh2` принимает свой `SSHSocket`. Пример моста — `tool/ws_bridge.dart` в пакете.

- Обязательно: мост с аутентификацией, allow-list целей, лимитами и проверкой `Origin`; проверка ключа хоста в приложении; `known_hosts` в браузере или на сервере. Плюс всё из раздела 3, без чего не стартует оболочка приложения.
- Ломается: локальный PTY на машине пользователя. Виртуальный Host этому варианту не мешает и может жить рядом.
- Объём: L. Риск: мост как открытый прокси.

### B. Удалённый PTY через `portable_pty`

На web пакет — клиент WebSocket или WebTransport к PTY-серверу на целевой машине.

- Обязательно: сервер на каждой машине, аутентификация, TLS, защита от cross-site WebSocket hijacking.
- Объём: XL. Свой сервис удалённого выполнения. Виртуальный Host его не заменяет: там нет настоящего TTY и чужих процессов.

### C. Linux в браузере через WASM

WebVM, v86 и аналоги. Раньше это был единственный способ выполнить команду без сервера.

- Сейчас этот объём нужен только если требуется полный дистрибутив и произвольные бинарники. Подмножество bash и файлы агента уже даёт виртуальный Host.
- Объём, если всё же понадобится: L–XL. Лицензия движка в проекте не проверялась.

### D. VNC или noVNC

Картинка рабочего стола вместо текста. Для инструментов с текстовым выводом неудобно. Объём: XL.

### E. Web только для просмотра

История чатов и управление desktop- или мобильным приложением. Агент в браузере команды не выполняет. Объём: M. Виртуальный Host этот вариант не закрывает: там исполнение есть, а синхронизации с другим устройством нет.

### F. Web-песочница на виртуальном Host

Уже написанное исполнение плюс оболочка приложения, которая стартует в браузере. Локальный и SSH-рантаймы в эту сборку не входят.

- Обязательно: условные импорты или отдельная точка входа, чтобы DI не тянул `portable_pty` и `dartssh2`; web-база drift для чатов и постоянного слоя VFS; журнал, логи команд и блокировка экземпляра без `dart:io`; секреты с понятным для пользователя смыслом `localStorage`; вложения из байтов выбора файла, а не из `File`; ветка `AppPlatform` для браузера, которая не создаёт локальный Host; проверка CORS OpenRouter. `InMemoryVfsStore` можно взять как образец хранилища, но постоянный слой всё равно нужен, иначе файлы агента пропадут вместе с вкладкой.
- Ломается: доступ к компьютеру пользователя и к SSH. Оболочка остаётся подмножеством из `docs/shell.md`. `/tmp` по-прежнему живёт до выгрузки процесса. Фоновых команд нет.
- Объём: M–L. Исполнение писать заново не нужно. Основная работа — отделить нативный граф и заменить файловое хранилище.

### G. Удалённый Host по WebSocket

Идея, в коде её нет. Перспективное направление для реальной машины пользователя: телефон, другой компьютер и будущий браузер подключаются одним протоколом.

На машине с файлами запускается сервер. Он слушает WebSocket и печатает в консоль данные подключения: адрес и секрет, который сгенерировал сам. В приложении их вводят так же, как адрес SSH-хоста, и сохраняют в записи хоста. Клиент для агента — обычный `HostRuntime`. Сервер выполняет вызовы уже написанным `LocalHostRuntime`: запись идёт в настоящие файлы, команды — в оболочку ОС и PTY.

Протокол повторяет три входа рантайма. Потока байтов терминала недостаточно: файловые инструменты идут через `perform`, без PTY.

- `perform(HostOp)` — чтение, запись, поиск, `stat`. Содержимое файла едет в stdin, как у локального Host. `ShellAdapter` остаётся на сервере, рядом с ОС.
- `run` — строка, которую написала модель.
- `openTerminal` — отдельный канал: вывод, ввод, размер, pid, код выхода.

Процесс живёт на сервере. Отписка клиента его не останавливает: так уже описан `HostRuntime`. Остановка — отдельная команда `kill`. Обрыв сокета — `ExecDone(connectionLost: true)`. Фоновый запуск доживает на сервере и отдаёт результат после повторного подключения. Закрытый процесс сервера обрывает хост.

Секрет из консоли обязателен: открытый порт без секрета — это оболочка для любого, кто его видит. С другой машины нужен `wss://` и проверка `Origin`. Токен в query string не кладётся.

- Обязательно: новый вид Host, клиентский рантайм, сервер поверх `LocalHostRuntime`, протокол кадров, повторное подключение для фоновых команд. Web-клиент дополнительно требует оболочку из раздела 3. Сам рантайм может быть на чистом Dart и не тянуть `portable_pty` и `dartssh2`.
- Ломается: доступ к машине, на которой сервер не запущен. SSH-сервер без нашего процесса по-прежнему вариант A. Виртуальный Host этот вариант не заменяет и остаётся песочницей.
- Объём: M–L в текущем desktop- и мобильном приложении. Цикл агента уже ходит в `HostRuntime`.

## 5. Сравнение

| Критерий | A. SSH-мост | B. Удалённый PTY | F. Виртуальный Host | G. Удалённый Host |
|---|---|---|---|---|
| Уже есть в проекте | нет | нет | исполнение есть, web-оболочки нет | граница `HostRuntime` есть, сервера нет |
| Машина пользователя | SSH-сервер | да, со своим PTY-сервером | нет, песочница | да, где запущен наш сервер |
| Файлы и терминал одним протоколом | да, внутри SSH | только PTY | файлы VFS, терминала нет | да: `perform`, `run`, `openTerminal` |
| Полный bash и чужие бинарники | да | да | нет, подмножество | да, это локальный рантайм |
| Свой сервер | мост к TCP | PTY-сервер | хостинг страницы | процесс на машине, секрет в консоли |
| Риск | открытый прокси | удалённый shell | изоляция VFS | удалённый shell, секрет сопряжения |
| Оставшийся объём | L | XL | M–L | M–L в приложении; web-клиент ещё требует раздел 3 |

Варианты C, D и E в таблице не повторяются. WASM-Linux нужен только ради полного дистрибутива. Картинка рабочего стола не стыкуется с текстовыми инструментами. Просмотр без исполнения — отдельный продукт.

Для песочницы в браузере реалистичный путь — F. Для реальной машины пользователя перспективное направление — G: оно покрывает файлы и PTY одним протоколом поверх уже написанного локального рантайма и работает до появления web-сборки (телефон или другой компьютер подключаются к серверу на машине). A остаётся для SSH-сервера, на котором наш процесс не запущен. B перекрывается вариантом G, отдельный PTY-сервер `portable_pty` для этого не нужен.

## 6. Безопасность

Для любого варианта с сокетом (A, B, G):

- только `wss://`, проверка сертификата и `Origin`;
- токен не в query string;
- allow-list `host:port`, лимиты кадров, соединений и таймаутов;
- проверка ключа SSH в приложении;
- пароли и ключи в браузере по умолчанию не сохранять; если сохранять — с предупреждением и с ключом шифрования не из того же `localStorage`;
- CSP с `connect-src` на разрешённые адреса;
- ввод с клавиатуры в PTY не передаётся, как и на остальных платформах.

Для F граница уже в коде и её нельзя ослабить ради web: нет процессов, нет эскалации, снимок только для чтения, квота на базу и `/tmp`, состояние оболочки не переживает `run_command`. Браузер добавляет другое: XSS читает и `localStorage`, и базу во вкладке. Секреты и содержимое VFS оказываются в одном профиле браузера.

Для G секрет сопряжения печатается в консоли машины и хранится у клиента как пароль хоста. Сервер принимает только этот секрет и не проксирует произвольные адреса. Пока процесс сервера жив, на нём же живут фоновые команды.

## 7. Ограничения браузера

- Фоновая вкладка троттлит таймеры и может закрыть WebSocket. Для F долгий запуск всё равно в этой вкладке: фоновых команд нет, отмена — закрытие потока, а не `kill`. Для G процесс остаётся на сервере, клиент после обрыва подключается снова.
- Оболочка и апплеты крутятся в том же изоляте, что и UI. Между `await` к VFS работа синхронная; тяжёлый `grep` или архив на большой ФС остановит отрисовку. На web вынести это в изолят сложнее, чем на VM.
- `sqlite3.wasm` и Flutter web увеличивают первую загрузку.
- Чужие файлы пользователя в VFS сами не попадают. Выбор файла — File System Access API (Chromium) или `input`, и это отдельный шаг, не команда `cp`.

Эти пункты в проекте не измерялись.

## 8. Что уже сделано и как это связано с web

- Виртуальный Host: исполнение, ФС и инструменты без ОС. Это и есть недостающий кусок песочницы из старого варианта C.
- `HostRuntime` уже разделяет `perform`, `run` и `openTerminal`. Удалённому Host (вариант G) остаётся сериализовать эти входы. `ExecDone.connectionLost` для обрыва соединения тоже есть. Вида хоста и сервера нет.
- `portable_pty` вместо `flutter_pty`: локальный PTY на сервере варианта G берётся из `lib/host/portable_pty_launcher.dart`. Отдельный транспорт `portable_pty` для браузера (вариант B) для этой идеи не нужен.
- Вложения уходят модели содержимым. Загрузчик всё ещё читает путь через `dart:io`.
- Терминал только показывает вывод. У виртуального Host терминала нет, карточка команды идёт потоком stdout/stderr.
- Мобильный SSH: Android держит соединение foreground-сервисом. К web это не относится.

## 9. Открытые вопросы

1. CORS OpenRouter из браузера — по-прежнему не проверен.
2. Нужен ли вообще WASM-Linux, или достаточно подмножества виртуальной оболочки.
3. Поведение `desktop_drop` на web. Для F вложения можно собирать из байтов `file_selector`, не из drag-and-drop.
4. `known_hosts` на мосте или в браузере — только если будет вариант A.
5. Кто держит мост — только для A. Для G сервер запускает сам пользователь на своей машине.
6. Safari и WebSocket в фоне — для A и G. Для F вкладка, которую выгрузили, теряет `/tmp` и незаконченный запуск; постоянный слой переживёт выгрузку только вместе с web-базой. Для G вкладка теряет сокет, процесс на сервере остаётся.
7. Как отрезать локальный и SSH-рантаймы от web-сборки, не раздвоив цикл агента.
8. Куда класть SQLite в браузере и как в той же базе сохранить постоянный слой VFS.
9. Формат кадра варианта G: `HostOp`, stdin, поток `ExecEvent`, отдельный канал терминала, повторное подключение к уже идущей команде.
10. Как долго сервер варианта G хранит секрет и что делать при перезапуске: печатать новый или оставлять прежний.
